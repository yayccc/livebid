# React 编码规范与 AI 协作指南

本规范约束 `mobile-user` 的代码组织、TypeScript、React、数据通信、样式组织、依赖引入和 AI 协作规则。通用体验、移动端布局、交互反馈和可访问性以 `用户端设计规范.md` 为准；具体业务范围、页面形态和接口字段以需求文档与接口文档为准。

本规范参考 React 官方文档、TypeScript 官方手册、Vite 官方模板实践，以及 Airbnb JavaScript / React JSX Style Guide，并结合本项目的 AI 协作开发场景整理。不要照搬外部规范中的过时类组件写法，本项目默认使用函数组件和 Hooks。

参考来源：

- React 官方 Hooks 规则：https://react.dev/reference/eslint-plugin-react-hooks/lints/rules-of-hooks
- TypeScript Handbook：https://www.typescriptlang.org/docs/handbook/intro.html
- Airbnb JavaScript Style Guide：https://github.com/airbnb/javascript
- Airbnb React/JSX Style Guide：https://javascript.airbnb.tech/react/
- Vite 官方文档：https://vite.dev/

## 基本原则

- 优先使用函数组件、Hooks 和 TypeScript。
- 组件保持小而清晰，一个组件只负责一个明确的 UI 或业务职责。
- 业务逻辑、数据请求、状态管理和 UI 展示分层组织，避免全部写进页面组件。
- 不为了“未来可能需要”提前抽象，先让代码直接、可读、可测试。
- AI 生成代码后必须能被人类快速理解，因此命名要准确，文件职责要稳定。

## 推荐目录结构

```text
src/
  assets/              静态资源
  components/          通用 UI 组件
  features/            按业务功能组织代码
  hooks/               通用 Hooks
  lib/                 无框架依赖的工具函数
  pages/               路由级页面壳组件
  services/            API、实时通信等外部通信封装
  stores/              跨页面共享状态
  styles/              全局样式、变量、主题
  types/               跨模块共享类型
```

当前项目较小时，不需要提前创建完整目录。功能代码优先放在 `features/<feature-name>/` 中；只有多个功能都会复用的代码，才提升到 `components/`、`hooks/`、`lib/` 或 `types/`。

`pages/` 只放路由级壳组件或页面装配入口。具体业务实现、局部组件和业务 Hook 优先放在对应 `features/` 中，避免 `pages/` 变成大而全的业务目录。

## TypeScript 规范

- 禁止随意使用 `any`；外部未知数据优先用 `unknown`，再做类型收窄。
- 组件 props 类型命名为 `ComponentNameProps`。
- 默认使用 `type` 描述对象类型；遇到扩展、声明合并或第三方库约定时使用 `interface`。
- 复杂状态优先使用联合类型表达，例如 `idle | loading | success | error`。
- API 返回值、表单值和实时事件都应有明确类型。
- 跨模块共享类型放在 `types/`，单一功能内部使用的类型优先靠近对应 feature。

## React 规范

- Hooks 只能在组件或自定义 Hook 的顶层调用，不能写在条件、循环或普通函数中。
- 能从 props 或已有 state 推导出的值，不要重复存入 state。
- `useEffect` 只用于同步外部系统，例如请求、订阅、定时器、浏览器存储和 DOM API。
- `useMemo`、`useCallback` 只在依赖稳定性或性能确有需要时使用。
- 事件处理函数命名使用 `handleXxx`，传给子组件的回调使用 `onXxx`。
- 列表渲染使用稳定 key，不使用会随渲染变化的随机值。
- 组件渲染逻辑保持纯粹，副作用放在 effect、自定义 Hook 或 service 中。

## 数据与通信

- 接口请求集中封装，不在组件中散落裸 `fetch`。
- 实时通信逻辑集中封装，连接、重连、关闭、错误处理和事件类型要明确。
- 页面卸载或切换上下文时，应清理连接、计时器和监听器。
- 页面组件优先消费整理后的数据、状态和回调，不直接解析复杂响应结构。
- 错误结构应统一处理，避免每个页面重复解析同类错误。
- 页面内临时状态优先放在组件本地；跨页面共享状态再提升到 store。
- 服务端数据避免维护多份副本；如引入请求缓存库，应让缓存成为服务端数据的主要来源。

## 页面实现

- 路由级页面负责组织页面结构，不承载过多底层数据转换和外部通信细节。
- 核心业务交互应拆成独立组件或自定义 Hook，避免堆在单个页面文件中。
- 关键业务流程应显式处理 loading、disabled、error 和可重试状态。
- 暂未接入的能力应展示明确占位或提示，不使用假数据伪装成真实功能。
- 需求不明确时，先记录假设或向上确认，不把猜测写成复杂实现。

## 样式组织

- 全局样式应保持克制，主要放置 reset、基础排版、移动端基础行为、主题变量和少量确有必要的全局规则。
- 组件样式应靠近组件或归属于功能模块。
- class 命名表达结构和语义，不使用颜色、字号、间距作为主要命名。
- 不在组件中硬编码大量重复内联样式。
- 重复样式出现三次以上再考虑提取。
- 具体视觉取值和移动端体验规则以 `用户端设计规范.md`、需求文档或设计稿为准。

## 依赖引入

- 新增重要运行时依赖前，应说明用途、替代方案，以及为什么当前内置能力或已有依赖不够。
- 新增依赖需要关注包体积、维护状态、类型支持、样式体系和运行时复杂度。
- 小型开发工具、类型包或已有工具链的配套包，可以按实际需要轻量处理。
- 未安装的第三方库不要直接在代码中引入。

## AI 协作规则

- 修改前先确认当前任务所属模块，只改必要文件。
- 不主动重构无关代码，不删除用户已有代码，除非任务明确要求。
- 生成代码后检查类型、边界状态、空状态、错误状态和移动端布局。
- 每次新增公共组件、Hook 或工具函数，都要保证命名能让人从名称理解用途。
- 不根据规范文档臆造具体业务接口、页面能力或视觉方案。
- 若需求不明确，优先在文档、注释或回复中记录假设，不把猜测写死成复杂实现。
