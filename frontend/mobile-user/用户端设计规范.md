# mobile-user 通用设计规范

本文档只约束 `mobile-user` 前端的通用设计原则、移动端布局、交互反馈、组件分层、样式边界和可访问性。它不规定具体页面形态、品牌视觉、颜色、字体、业务模块和接口字段；这些内容以需求文档、接口文档和后续设计稿为准。

代码组织、TypeScript、React、依赖引入和 AI 协作编码规则以 `CODING_GUIDELINES.md` 为准。

## 一、适用范围

本文档适用于移动端 H5 前台项目的通用体验设计与页面实现约束。

它负责说明：

- 页面和组件如何保持一致、清晰、可维护。
- 移动端布局、触控、反馈和异常状态如何处理。
- 通用组件与业务组件如何划分职责。
- 设计规范与具体业务需求之间的边界。

它不负责说明：

- 应用主视觉、主题色、字体风格和品牌调性。
- 具体页面包含哪些业务功能。
- 具体按钮、卡片、浮层或业务信息应放在哪里。
- 接口路径、接口字段和后端能力清单。
- 目录结构、类型命名、状态库选型和第三方依赖选择。

## 二、通用原则

- 移动端优先，最小宽度按 `320px` 处理。
- 首屏应直接服务当前页面的核心任务，避免无关说明和装饰。
- 信息层级要清楚，主内容、主操作、关键状态和辅助信息应有明确优先级。
- 关键操作和异步操作必须有可感知的反馈。
- 暂未接入的数据和能力必须明确标识，不伪装成真实可用功能。
- 不为未来可能出现的页面提前增加复杂结构，先保证当前体验清晰、实现可维护。

## 三、移动端布局

### 1. 视口与安全区

- 使用移动端优先的布局方式，再向大屏扩展。
- 需要占满视口的页面应兼容移动浏览器地址栏和工具栏变化；具体使用 `100dvh`、CSS 变量或其他方案由实现决定。
- 固定在顶部或底部的元素需要处理安全区：

```css
padding-top: env(safe-area-inset-top);
padding-bottom: env(safe-area-inset-bottom);
```

- 固定底部导航、底部操作栏和浮层时，主体内容应预留足够空间，避免关键内容和操作被遮挡。
- 横屏场景至少保持基础可用；若业务只适合竖屏，可以给出明确提示。

### 2. 页面结构

- 页面应围绕“主内容、主操作、辅助信息、反馈状态”组织。
- 同一屏内避免堆叠过多同级信息；必要时使用抽屉、弹窗、详情页、折叠区或二级页面承载次要内容。
- 列表、详情、表单和空状态应有稳定结构，加载前后尽量减少布局跳动。
- 固定格式元素应设置稳定尺寸，例如导航项、工具栏按钮、计数器、封面区域和底部操作区。

### 3. 文本与溢出

- 文本不能溢出按钮、标签、导航项、卡片和浮层。
- 长标题、昵称、商品名等内容必须处理换行、省略或最大宽度。
- 按钮文案过长时优先调整文案，而不是强行缩小到不可读。
- 不使用随视口宽度变化的字号。
- 字间距保持默认，除非设计稿明确要求。

### 4. 卡片与层级

- 卡片用于承载独立信息块，不用于包裹整页。
- 避免卡片套卡片。
- 同一块内容内部优先使用分组、分割线、间距和标题层级。
- 浮层、弹窗、抽屉出现时，应有明确的遮罩、关闭方式和层级关系。

## 四、信息与反馈

### 1. 数据展示状态

独立数据展示区域应按实际场景处理以下状态：

- 初始状态。
- 加载中。
- 成功状态。
- 空状态。
- 错误状态。
- 重试入口，若该操作可重试。

不是每个区域都必须同时具备全部状态；例如提交动作通常不需要空状态，静态内容也不需要加载状态。状态文案应说明当前发生了什么，以及用户下一步可以做什么。

### 2. 操作反馈

所有关键操作都应有反馈：

- 提交中：按钮 loading 或禁用重复提交。
- 成功：轻提示、局部刷新或状态更新。
- 失败：展示错误原因，必要时提供重试。
- 禁用：在用户可能疑惑时说明禁用原因。
- 危险操作：二次确认，并说明后果。

纯本地交互可以只提供按下态、选中态或展开收起状态，不要求套用异步反馈。

### 3. 表单

表单要求：

- 必填字段清晰标识。
- 错误信息靠近字段展示。
- 提交失败不清空用户已填写内容。
- 编辑表单应能正确回填已有数据。
- 同一页面不要混用多套表单状态管理方式。
- 键盘弹出时，输入框和提交按钮不能被不可恢复地遮挡。

### 4. 列表与分页

列表要求：

- 加载中保持布局稳定。
- 空列表展示明确空状态。
- 请求失败展示错误状态。
- 无限滚动应处理加载中、没有更多、失败重试和重复请求。
- 列表项点击区域要足够大，避免误触。

## 五、组件分层

### 1. 通用组件

通用组件不绑定具体业务语义，只承载可复用的交互和展示模式。

常见类型包括：

- 按钮与图标按钮。
- 搜索输入。
- 状态标签。
- 空、加载、错误状态。
- 安全区容器。
- 操作面板、确认弹窗和底部抽屉。

这些组件按实际需要建立，不要求提前创建完整清单。通用组件应通过参数接收配置，不直接写死业务字段、接口字段或页面文案。

### 2. 业务组件

业务组件可以包含具体业务语义，但应保持边界清晰：

- 页面组件负责组合页面结构。
- 业务组件负责局部展示和交互。
- 请求、实时通信和复杂数据转换不应散落在 UI 组件里。
- 业务组件不要越过所属模块直接操作其他模块内部状态。

### 3. 组件职责

- 一个组件只承担一个明确职责。
- 能由 props 或已有 state 推导出的值，不重复存入 state。
- 复杂交互优先拆成局部业务组件或自定义 Hook。
- 组件内部避免混合大量数据请求、状态转换和视图细节。

## 六、样式边界

- 全局样式应保持克制，主要放置 reset、基础排版、移动端基础行为、主题变量和少量确有必要的全局规则。
- 组件样式应靠近组件或归属于功能模块。
- 颜色、字号、间距、阴影、圆角等视觉取值应通过主题变量或设计稿决定，本文档不固定具体值。
- class 命名表达结构和语义，不使用颜色、字号、间距作为主要命名。
- 重复样式出现三次以上再考虑提取。
- 不在组件中硬编码大量重复内联样式。

## 七、可访问性

- 可点击元素要使用语义合适的元素，或补充必要的 ARIA 属性。
- 图标按钮必须有可理解的 `aria-label` 或文本替代。
- 表单输入要关联 label。
- 弹窗和抽屉要有明确关闭方式。
- 错误提示不能只依赖颜色表达。
- 关键触控目标建议不小于 `44px * 44px`；紧凑场景应通过外层点击区域保证可点性。

## 八、协作边界

当根据本文档进行设计或实现时，应遵守：

1. 只把本文档当作通用设计和体验约束。
2. 不根据本文档臆造具体业务页面、接口、视觉主题或产品能力。
3. 具体页面、字段、接口、视觉方案和业务流程以用户需求、需求文档和当前代码为准。
4. 没有真实后端能力的数据，不要伪装成可用生产功能。
5. 若通用规范与具体业务需求冲突，以业务需求为准，并在实现或文档中记录原因。
