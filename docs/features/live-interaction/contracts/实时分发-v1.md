# 直播互动实时分发契约 v1

> Status: proposed
> Authority: 本文负责 Redis Key、Lua 原子提交、房间广播频道、AI 输入逻辑分片和实时投递语义。
> Non-authority: 消息字段和 RPC 见 `消息与接口-v1.md`；AI 内部调度见 ai-service 设计。
> Updated-at: 2026-07-17 +08:00

## 一、基础选择

P0 使用 Redis 数据结构与 Pub/Sub：写路径短、延迟低，符合弹幕和 AI 观察“新鲜度高于可靠积压”的需求。RocketMQ 不进入实时互动闭环；以后如需审计、训练样本或统计，可在异步旁路增加。

P0 可以部署单机 Redis，但 Key 和频道从第一天按 Redis Cluster 规则设计。实际 Cluster、Sharded Pub/Sub 和扩容运维属于后续能力，不改变命名契约。

## 二、Redis Key

所有同一房间原子提交涉及的 Key 使用相同首个 hash tag `{room:<room_id>}`：

| Key 模板 | 作用 |
| --- | --- |
| `interaction:{room:<room_id>}:seq` | 房间序号 |
| `interaction:{room:<room_id>}:recent` | 有界短历史 |
| `interaction:{room:<room_id>}:req:user:<user_id>:<request_id>` | 用户发布完整幂等结果 |
| `interaction:{room:<room_id>}:rate:user:<user_id>` | 用户基础频控 |
| `interaction:{room:<room_id>}:session:<live_session_id>:req:ai:<decision_id>` | AI 发布完整幂等结果；语义按场次隔离、物理上与房间提交同槽 |
| `interaction:{room:<room_id>}:session:<live_session_id>:rate:ai` | interaction 侧 AI 每房间硬上限 |

例如房间 4001 的 tag 是 `{room:4001}`。`live_session_id` 不再使用第二个花括号，避免 Cluster 脚本跨槽。

AI 自有跨决策状态使用 session tag，由 ai-service 设计维护：`ai:{session:<live_session_id>}:...`。它不参与 interaction 的房间提交脚本。

## 三、Lua 原子提交

P0 确定使用 Lua，不再把原子边界留作实现阶段选择。用户与 AI 两类写入共用提交骨架：

```text
读取幂等结果；命中则返回首次完整消息
-> 检查并写入对应频控/硬上限
-> INCR room_seq
-> 将 room_seq 写入服务端生成的消息草稿
-> LPUSH recent + LTRIM + EXPIRE
-> SET 完整幂等结果及 TTL
-> 返回完整规范消息
```

内容校验、P0 内网调用边界、房间状态、AI 场次和新鲜度在脚本前完成；脚本负责单房间 Redis 状态的一致提交。幂等结果必须保存完整消息和事件信封，不能只保存 `message_id`，以便结果未知时按原 ID 重试发布。

脚本提交与 Pub/Sub 不是分布式事务。脚本成功后进程崩溃可能导致在线消费者漏收，但消息仍在 recent；这是尽力投递的已知边界，不为此引入可靠 MQ。调用方在结果未知时用原幂等键重试，interaction-service 可以重发同一事件；客户端必须去重。

## 四、房间广播

频道固定为：

```text
interaction:room:{room:<room_id>}:fanout:v1
```

载荷固定为 [EventEnvelope](./消息与接口-v1.md#三事件信封)。interaction-service 是唯一发布者；所有 ws-gateway 实例只订阅本机有连接的房间。

v1 房间 fan-out 的 `expires_at_ms = occurred_at_ms + 30_000`。网关收到已过期实时事件时丢弃并计数，不能将迟到 Pub/Sub 当作新消息；用户随后仍可通过 recent 看到已提交消息。

每个网关实例使用一个网关级 Pub/Sub 管理器动态管理多个频道：

1. 本机首个连接进入房间时订阅并等待确认。
2. 订阅成功后查询 recent；订阅期间到达的事件与 recent 按 `message_id` 合并、按 `room_seq` 排序。
3. 最后一个本地连接退出后延迟退订，避免频繁抖动。
4. Redis 重连后按本地房间引用计数恢复全部订阅。
5. 不为每个房间创建独立 Redis 连接，也不全局 `PSubscribe` 所有房间。

## 五、AI 输入逻辑分片

逻辑分片数量从 v1 固定为 64，频道为：

```text
interaction:ai:input:{bucket:b00}:v1
...
interaction:ai:input:{bucket:b63}:v1
```

分片算法固定为：

```text
raw = strconv.FormatInt(live_session_id, 10)  // 十进制，无前导零和空白
bucket = CRC32-IEEE(UTF-8(raw)) % 64
channel = b + 两位小写十六进制 bucket
```

因此 bucket 取值 `b00` 到 `b3f`。配置可以限制实例实际订阅哪些 bucket，但不得修改分片数、算法或频道格式。

P0 只部署一个 AI 消费实例并订阅全部 64 个逻辑频道；固定分片的目的在于以后扩容不迁移生产契约。P1 才增加多实例租约和 bucket 分配，不能让多个实例无协调地长期消费同一 bucket。

AI 输入满足以下条件才发布：

- interaction-service 已成功接纳的 `USER` 消息。
- 消息携带 live-service 当前有效的 `live_session_id`。
- AI 全局/房间输入开关允许。

v1 AI 输入的 `expires_at_ms = occurred_at_ms + 5_000`。ai-service 以自身当前时间比较并丢弃过期事件；时钟偏差纳入监控，不能由消费者自行扩大窗口。两条频道复用同一信封结构，但新鲜度由本节分别固定，不得共用一个含糊默认值。

AI 输入发布失败不回滚用户消息，也不使用户发送失败；记录指标后结束。输入订阅者断线期间的消息不补偿。

## 六、顺序与容量边界

- `room_seq` 只由 interaction-service 的 Lua 分配；网关和 AI 不得生成。
- recent 以 `room_id` 为维度保存有界条数与 TTL，返回时按 `room_seq` 升序。
- 房间广播和 AI 输入可能乱序、重复或丢失；消费者以 `message_id/event_id` 去重，不无限等待序号缺口。
- 热门房间压力由房间频道、网关本地连接扇出和限流承担；AI 的 64 分片不改变房间广播拓扑。
- 单房间成为 Redis Cluster 热点是该弱一致实时模型的已知取舍；需要再拆房间内写序列时必须升级契约版本，不能静默改变 `room_seq` 语义。
