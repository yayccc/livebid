# 直播互动消息与接口契约 v1

> Status: proposed
> Authority: 本文负责跨服务消息实体、事件信封、标识符、gRPC 语义、错误码和兼容规则。
> Non-authority: Redis Key/频道见 `实时分发-v1.md`；外部 JSON 见 ws-gateway 协议。
> Future-authority: 正式 `api/proto/interaction/v1/interaction.proto` 创建后，字段号、枚举值和 RPC 形状以 Proto 为准。
> Updated-at: 2026-07-17 +08:00

## 一、标识符

| 标识 | 生成者 | 语义与作用域 |
| --- | --- | --- |
| `room_id` | live-service | 长期存在的互动空间 |
| `live_session_id` | live-service | 一次业务直播；离线真人消息可空，AI 消息必填 |
| `request_id` | 客户端 | 同一用户、同一房间内一次发送及其重试 |
| `decision_id` | ai-service | 一次 AI 发布决策及其短重试，不承担跨实例意图防重 |
| `message_id` | interaction-service | 一条规范互动消息的全局唯一 ID |
| `event_id` | interaction-service | 一次规范事件的唯一 ID；重发同一已提交消息时保持不变 |
| `trace_id` | 链路入口 | 跨 WS、gRPC、Tool 和模型调用关联，不能用于业务幂等 |
| `room_seq` | interaction-service | 房间内递增弱顺序；允许间隙，不代表可靠投递 |

## 二、规范消息实体

`InteractionMessage` 只描述业务消息，不包含投递层 `event_id`、`trace_id` 和过期时间。

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `schema_version` | int32 | v1 固定为 `1` |
| `message_id` | string | interaction-service 生成 |
| `room_id` | int64 | 必填 |
| `live_session_id` | optional int64 | 真人消息可空；AI 消息必填 |
| `room_seq` | int64 | 同一房间递增 |
| `sender_type` | enum | `USER`、`AI_ASSISTANT`；`SYSTEM` 预留 |
| `user_id` | optional int64 | 仅 `USER` 存在，来自认证上下文 |
| `display_name` | string | 服务端确认的展示快照 |
| `assistant_role` | optional enum | AI 固定为 `LIVE_ASSISTANT` |
| `action_type` | optional enum | AI 使用 `ANSWER`、`REDIRECT`；`ATMOSPHERE` 预留 |
| `content_type` | enum | v1 只启用 `TEXT` |
| `content` | string | 规范化后的公开文本 |
| `reply_to_message_ids` | repeated string | AI 回答所覆盖的候选消息，可空 |
| `created_at_ms` | int64 | 服务端 Unix 毫秒时间 |
| `status` | enum | v1 固定 `VISIBLE`，为撤回扩展预留 |

`source_refs` 不进入公开消息或互动 RPC。AI 使用过的资料只进入脱敏决策审计，避免 interaction-service 承担没有消费方的字段。

## 三、事件信封

实时链路统一使用 `EventEnvelope<InteractionMessage>`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schema_version` | int32 | 信封版本，v1 为 `1` |
| `event_id` | string | interaction-service 生成 |
| `event_type` | string | v1 为 `interaction.message.created` |
| `occurred_at_ms` | int64 | 消息提交时间 |
| `expires_at_ms` | int64 | 消费方晚于此时间直接丢弃；不同频道的固定窗口见实时分发契约 |
| `trace_id` | string | 链路追踪 ID |
| `message` | InteractionMessage | 规范消息实体 |

房间广播与 AI 输入使用同一实体和信封。AI 输入只发布 `sender_type=USER` 且带当前有效 `live_session_id` 的事件；不得再次定义 `danmaku.created` 私有字段集。

## 四、gRPC 语义

### 4.1 PublishUserMessage

该接口在架构上只供 `ws-gateway` 调用。P0 通过私有网络和部署拓扑限制访问，暂不做密码学服务身份认证。请求包含：

- `request_id`
- `room_id`
- `content`
- `display_name_snapshot`

用户 JWT 由 ws-gateway 验证，`user_id` 从网关写入的调用 metadata 取得，不信任客户端请求体自报。P0 对该 metadata 的信任建立在 interaction gRPC 不对公网开放、只有网关能够访问的部署假设上。interaction-service 从 live-service 解析房间和可选当前场次，调用方不得指定 `live_session_id`。

响应返回完整 `InteractionMessage` 和 `idempotent_replay`。同一用户、房间和 `request_id` 重试必须返回首次提交的同一消息。

### 4.2 PublishAssistantMessage

该接口在架构上只供 `ai-service` 调用。P0 同样依靠私有网络和部署拓扑限制访问，暂不验证 service JWT。请求包含：

- `decision_id`
- `room_id`
- `live_session_id`
- `action_type`
- `content`
- `reply_to_message_ids`
- `valid_until_ms`

interaction-service 必须重新确认 AI 开关、当前场次和过期时间；AI 不得指定发送者、昵称、`message_id`、`event_id` 或 `room_seq`。同一场次和 `decision_id` 的短重试返回首次提交的同一消息。

### 4.3 GetRecentMessages

请求包含 `room_id` 和可选 `limit`。响应包含按 `room_seq` 升序的有界消息、`latest_room_seq` 和当前可选 `live_session_id`。它只用于进入房间与轻量重连，不承诺补齐所有缺口。

## 五、P0 信任边界与后续认证

P0 不实现 service JWT、mTLS 或服务令牌，采用以下明确的过渡约束：

1. interaction gRPC 只监听内部网络，不经 api-gateway、Ingress 或公网暴露。
2. 网络和部署配置只允许 ws-gateway、ai-service 及必要运维探针访问。
3. ws-gateway 验证用户 JWT 后写入现有 `livebid-auth-subject-type`、`livebid-auth-subject-id`；interaction 在该受控拓扑下暂时信任这些 metadata。
4. `PublishUserMessage` 与 `PublishAssistantMessage` 仍保持独立 RPC，Handler 固定其发送者类型，调用方不能通过请求字段切换身份。
5. trace 使用标准 `traceparent`；过渡期可兼容 `x-trace-id`。

这只是开发阶段的信任模型，不等同于服务认证。统一服务认证后，在 gRPC interceptor 增加 `CallerService` 校验，并按 `ws-gateway -> PublishUserMessage`、`ai-service -> PublishAssistantMessage` 授权；不得修改业务 RPC 或消息字段。上线公网或引入不可信内部调用方前必须完成该加固。

## 六、gRPC 状态映射

| 状态 | 场景 |
| --- | --- |
| `InvalidArgument` | 缺字段、格式错误、空内容、超长或非法枚举 |
| `Unauthenticated` | 用户消息缺少有效终端用户身份；后续也用于服务认证失败 |
| `PermissionDenied` | 房间未发布、互动关闭；后续也用于调用服务无权使用 RPC |
| `FailedPrecondition` | AI 场次已结束/切换、回复过期、业务状态不满足 |
| `ResourceExhausted` | 用户频控或 AI 房间硬上限 |
| `Unavailable` | Redis、live-service 等必要依赖不可用 |
| `Internal` | 非预期服务端错误 |

只有 `Unavailable` 和调用超时结果未知时允许使用原幂等键进行有界重试；参数、权限和前置条件错误不得盲重试。

## 七、顺序、投递和兼容

- gRPC 返回成功表示消息已在 interaction-service 提交，并完成一次房间发布尝试；不表示所有在线客户端已收到。
- Redis Pub/Sub 是至多尽力实时投递，订阅断开期间不补发；客户端依赖 `message_id` 去重、以 `room_seq` 弱排序。
- AI 输入允许丢失和过期，不建立积压重放；AI 不能把 `room_seq` 间隙理解为必须补洞。
- 新版本只追加字段或枚举；消费者必须忽略未知字段。删除/改义需要新版本频道与兼容窗口。
- `schema_version` 与频道版本共同校验；无法识别的主版本必须丢弃并计数。
