# 直播互动实施路线

> Status: proposed
> Authority: 本文唯一负责当前状态、P0/P1/P2 能力边界和迁移顺序。
> Non-authority: 本文不复制消息字段、Redis Key 或服务内部算法。
> Applies-to: `refactor/interaction-service`
> Updated-at: 2026-07-17 +08:00

## 一、当前状态

截至 2026-07-17：

- `ws-gateway` 已实现直管文本弹幕 V1，包括准入、幂等、频控、recent、房间 Pub/Sub 和旧 AI 输入发布。
- `interaction-service` 和 `ai-service` 尚未创建代码、Proto 或部署单元。
- live Proto 已追加 `visibility`、`chat_enabled`、`current_live_session_id` 字段；可修改房间策略的 `UpdateLiveRoom` RPC、数据库、状态机和用户入口尚未落地。
- 本专题文档描述目标架构，不表示运行行为已经迁移。

## 二、路线原则

“基础架构一次完成”不是首版部署所有复杂基础设施，而是首版固定以后迁移代价高的边界：

| P0 必须固定 | 可以后续实现而不改契约 |
| --- | --- |
| room/session 语义、消息实体、事件信封、RPC 与枚举 | Redis Cluster 实际部署、Sharded Pub/Sub |
| Redis hash tag、Lua 提交边界、频道和 64 分片算法 | 多 AI 实例租约和公平调度 |
| gRPC interceptor 扩展点、trace、最终安全开关 | 统一 service JWT、mTLS 或 service mesh identity |
| Tool/模型/知识/调度可替换接口 | 向量库、完整 RAG、多模型路由 |
| 单一写入口与单写迁移开关 | 主动氛围、私聊、完整审核和长期历史 |

后续阶段增加实现，不重新定义字段含义、散列算法或服务所有权。

## 三、P0：可扩展基础与自动问答闭环

基础架构：

1. 冻结并补齐 live-service `UpdateLiveRoom` Proto，落地持久房间、业务场次和带 client/generation 防迟到保护的媒体状态分层。
2. 创建 interaction Proto 和 trace 传播；服务端口只开放在受控内部网络，并保留统一认证 interceptor 扩展点。
3. 创建 interaction-service，使用 Cluster-ready Key 与 Lua 原子提交。
4. 网关改为 gRPC 发布、动态订阅房间频道、订阅后合并 recent。
5. 固定 64 个 AI 输入逻辑分片；部署一个 AI 实例订阅全部分片。
6. 从第一天提供全局开关、room/shop allowlist、AI 硬上限和单写切换开关。
7. 代码接口隔离 Redis、live client、Tool、模型、知识和调度实现。

首个业务闭环：

1. 已发布房间在线/离线真人文本互动。
2. 业务直播中真人消息的低延迟 AI 输入。
3. 规则过滤、短窗口聚合、候选评分和选择性回答。
4. 动态 Tool 安全投影、一次受约束模型生成。
5. `ANSWER/REDIRECT` 经 interaction 回写；AI 失败不影响真人弹幕。

P0 明确不做 RAG、向量库、多实例租约、公平调度和主动氛围消息。

## 四、P1：知识与水平扩展

- 商家/商品知识导入、版本化切片、Embedding、向量检索和引用审计。
- 两个以上 AI 实例的 bucket 租约、故障转移、session inflight 和意图预留强化。
- 跨房间加权公平调度、模型配额和更完整的离线评测集。
- 商家侧 AI 策略配置和灰度范围管理。
- Redis Cluster 与 Sharded Pub/Sub 按容量结果落地；频道和 hash tag 不变。

## 五、P2：主动场控与治理

- 接入开播、商品切换、开拍、临近结束等生命周期事件，启用 `ATMOSPHERE`。
- 主播副驾、私人问答或高频问题卡片等新交互形态。
- 禁言、撤回、内容审核、长期消息或可靠审计旁路。
- 训练样本回流、A/B 实验、复杂多模型与 tool-calling Agent。
- 在生产化前统一增加服务身份认证与 RPC 权限矩阵，可选 service JWT、mTLS 或 service mesh identity。

## 六、迁移顺序

1. **live 依赖先行**：实现房间可见性、`chat_enabled`、`StartLive/EndLive` 场次语义和离线入口。
2. **契约先行**：评审并创建 interaction Proto 与共享事件结构；P0 使用私有网络信任模型，统一服务身份认证后置。
3. **interaction 旁路验证**：新服务写隔离 Key，压测 Lua、recent 和 fan-out，不接管生产入口。
4. **网关单写切换**：按 room allowlist 切换到 interaction；同一请求禁止新旧链路双写或双广播。
5. **AI 观察灰度**：单实例订阅全部 64 bucket，先只记录决策不公开输出。
6. **AI 输出灰度**：仅 allowlist 房间开放 `ANSWER/REDIRECT`，观察安全、重复和时延。
7. **删除旧写路径**：稳定后移除 ws-gateway 业务 Redis 写入和旧 RocketMQ/Redis AI 双链路配置。

回滚只切换入口所有权，不复制消息：切回旧链路前先停止新入口，任何时刻每个 room 只能有一个 `room_seq` 分配者。

## 七、P0 验收门槛

- 离线发布房间可互动，消息不带 session；开播后消息携带当前 session。
- 用户与 AI 消息只有 interaction-service 分配 `message_id/event_id/room_seq`。
- Lua 并发与结果未知重试不产生双消息；所有 Key 可在同一 Cluster slot 执行。
- 多网关实例只向本地连接转发，并能在 Redis 重连后恢复动态订阅。
- 单 AI 实例能消费全部 64 bucket；关闭 AI 后 interaction 最终拒绝回写。
- 场次结束、切换或回复过期时拒绝 AI 结果；模型失败不阻断真人互动。
- 活跃文档无第二套字段、频道或阶段定义，旧 RocketMQ 方案只存在于 archive。

## 八、仍可后置的选择

模型供应商、向量数据库产品、Embedding 模型、商家知识导入 UI 和统一服务认证方案可在相应阶段选择。它们必须实现已冻结接口，不能反向改变公开消息、分片或单写边界。
