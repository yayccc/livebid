# mobile-user 用户端聚合接口设计

## 一、设计目标

本文档定义 `mobile-user` 第一版需要的用户侧聚合 HTTP 接口。聚合接口由 `api-gateway` 对外提供，前端只访问 `api-gateway` 和 `ws-gateway`，不直接调用 `live-service`、`auction-service`、`goods-service`、`shop-service` 等内部服务。

第一版首页采用上下滑直播间流：

```text
预览态：展示直播画面 + 基础信息 + 进入按钮
房间态：展示直播画面 + 竞拍 + 商品 + 弹幕/系统消息 + 出价入口
```

聚合接口需要支持：

- 首页直播间流分页加载。
- 预览态播放地址获取。
- 点击进入直播间后的房间详情聚合。
- WebSocket 断线或事件丢失时的竞拍快照兜底。
- 当前最高价、下一口出价金额、倒计时和领先用户展示。

## 二、通用约定

### 2.1 基础路径

用户端聚合接口统一放在：

```text
/api/user/live
```

说明：

- `/api/live/...` 保留给直播基础资源接口。
- `/api/merchant/...` 保留给商家端聚合接口。
- `/api/user/live/...` 明确表示面向普通用户端页面体验的聚合接口。

### 2.2 响应格式

所有 HTTP JSON 响应统一使用：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

失败响应：

```json
{
  "code": 400,
  "message": "请求参数无效，请检查后重试",
  "data": null
}
```

约定：

- `code = 0` 表示成功。
- 失败时 `code` 使用 HTTP 状态码。
- `message` 面向前端展示或日志排查，应使用中文业务语义。
- 失败时 `data` 可以为 `null` 或省略；建议统一返回 `null`。

### 2.3 时间格式

HTTP 聚合接口中的时间字段统一使用 Unix 毫秒：

```text
1780000123000
```

原因：

- 与 `ws-gateway` WebSocket 事件时间格式保持一致。
- 前端做倒计时、排序、差值计算更直接。

若底层服务返回 `YYYY-MM-DD HH:mm:ss` 或 RFC3339，`api-gateway` 负责转换为 Unix 毫秒。

### 2.4 金额格式

金额字段统一使用整数，单位为分：

```json
{
  "current_price": 18000
}
```

前端负责格式化展示为人民币金额。

### 2.5 鉴权约定

首页预览类接口不强制登录：

- 游客可以浏览直播间流。
- 游客可以获取播放地址。
- 游客可以进入房间态观看直播和查看竞拍信息。
- 游客不能出价。

需要用户身份时，前端携带：

```text
Authorization: Bearer <access_token>
```

带 token 且校验成功时，聚合接口可以返回用户态字段，例如：

- `viewer.is_logged_in`
- `viewer.can_bid`
- `viewer.user_id`

未带 token 时不返回敏感身份信息，用户态按游客处理。

### 2.6 安全边界

用户端聚合接口不能返回商家推流敏感信息：

- 不返回 `rtmp_push_url`。
- 不返回 `stream_code`。
- 不返回 `initial_stream_code`。
- 不返回推流密钥。
- 不返回内部 `stream_key_hash`。

用户端只能拿到播放需要的地址，例如：

- `webrtc_play_url`
- 后续可选的 `flv_play_url`
- 后续可选的 `hls_play_url`

## 三、接口清单

| 场景 | 方法 | 路径 | 登录 |
| --- | --- | --- | --- |
| 首页直播间流 | GET | `/api/user/live/feed` | 否 |
| 预览播放信息 | GET | `/api/user/live/rooms/{room_id}/preview` | 否 |
| 进入直播间聚合详情 | GET | `/api/user/live/rooms/{room_id}/entry` | 否，可带 token |
| 直播间竞拍快照 | GET | `/api/user/live/rooms/{room_id}/auction-snapshot` | 否，可带 token |
| 直播间竞拍记录 | GET | `/api/user/live/rooms/{room_id}/auction-records` | 否，可带 token |

首版必做：

- `GET /api/user/live/feed`
- `GET /api/user/live/rooms/{room_id}/entry`
- `GET /api/user/live/rooms/{room_id}/auction-snapshot`
- `GET /api/user/live/rooms/{room_id}/auction-records`

建议首版同时做：

- `GET /api/user/live/rooms/{room_id}/preview`

## 五、首页直播间流接口

### 5.1 接口定义

```text
GET /api/user/live/feed?page=1&page_size=10
```

### 5.2 查询参数

| 参数 | 类型 | 必须 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `page` | int | 否 | 1 | 页码，从 1 开始 |
| `page_size` | int | 否 | 10 | 每页数量，建议最大 20 |
| `cursor` | string | 否 | 空 | 后续推荐流游标，首版可不实现 |

首版可以只支持 `page` 和 `page_size`。如果同时传入 `cursor`，优先使用 `cursor`。

### 5.3 业务规则

1. 只返回 `status = living` 的直播间。
2. 优先返回 `media_stream_status = online` 的直播间。
3. 列表按后端默认顺序返回；首版不做复杂推荐。
4. 每个直播间可以返回预览播放地址，方便前端刷到后直接播放。
5. 如果播放地址生成成本较高，列表可不返回 `preview_stream`，前端刷到当前项时再调用预览播放接口。
6. 不能返回推流地址、推流码、stream key 等敏感字段。

### 5.4 聚合来源

| 数据 | 来源 |
| --- | --- |
| 直播间基础信息 | `live-service.ListLiveRooms` |
| 播放地址 | `live-service.GetLiveStreamInfo` 或后续用户侧播放方法 |
| 商铺公开信息 | `shop-service.GetShop` |
| 当前竞拍摘要 | `auction-service` 按直播间查询当前竞拍，若暂未实现可为空 |
| 商品摘要 | `goods-service.BatchGetGoods` |
| 在线人数 | `ws-gateway`/Redis 后续提供；首版可返回 0 或省略 |

## 六、预览播放信息接口

### 6.1 接口定义

```text
GET /api/user/live/rooms/{room_id}/preview
```

### 6.2 路径参数

| 参数 | 类型 | 必须 | 说明 |
| --- | --- | --- | --- |
| `room_id` | int64 | 是 | 直播间 ID |

### 6.3 业务规则

1. 用于首页预览态，前端刷到某个直播间时获取播放地址。
2. 直播间必须存在且未删除。
3. 首版建议只允许 `status = living` 的直播间返回可播放地址。
4. 媒体流离线时仍返回直播间基础信息，但 `stream.play_status = unavailable`。
5. 不返回竞拍、商品、弹幕或系统消息。
6. 不返回任何推流敏感字段。

## 七、进入直播间聚合详情接口

### 7.1 接口定义

```text
GET /api/user/live/rooms/{room_id}/entry
```

### 7.2 请求头

```text
Authorization: Bearer <access_token>
```

说明：

- 该请求头可选。
- 不带 token 时按游客处理。
- token 无效时建议返回 `401`，由前端清理本地登录态后以游客身份重试。

### 7.3 路径参数

| 参数 | 类型 | 必须 | 说明 |
| --- | --- | --- | --- |
| `room_id` | int64 | 是 | 直播间 ID |

### 7.4 业务规则

1. 用户点击“进入直播间”时调用。
2. 返回房间态首屏需要的全部静态和快照数据。
3. 直播间必须存在且未删除。
4. 首版建议只允许进入 `status = living` 的直播间。
5. 游客可以进入并查看直播、竞拍、商品信息，但 `viewer.can_bid = false`。
6. 登录用户如果账号状态正常，则 `viewer.can_bid = true`。
7. 当前没有竞拍时，`current_auction`、`goods`、`runtime` 可以为 `null`。
8. 不返回推流敏感字段。

### 7.5 聚合来源

| 数据 | 来源 |
| --- | --- |
| 直播间详情 | `live-service.GetLiveRoom` |
| 播放地址 | `live-service.GetLiveStreamInfo` 或后续用户侧播放方法 |
| 商铺公开信息 | `shop-service.GetShop` |
| 当前竞拍 | 建议新增 `auction-service.GetCurrentAuctionByRoom`；首版可由网关按 room 维度查询后聚合 |
| 商品详情 | `goods-service.GetGoods` 或 `BatchGetGoods` |
| 竞拍运行态 | `auction-service.GetAuctionRuntime` |
| WebSocket 地址 | 网关配置拼接 |

## 八、直播间竞拍快照接口

### 8.1 接口定义

```text
GET /api/user/live/rooms/{room_id}/auction-snapshot
```

### 8.2 业务规则

1. 用于房间态 WebSocket 断线重连、事件丢失、页面恢复前台后的状态兜底。
2. 返回当前直播间正在展示的竞拍快照。
3. 当前没有竞拍时返回 `current_auction = null`。
4. 如果请求携带用户 token，可返回 `viewer.can_bid` 等用户态字段。
5. 该接口不替代 WebSocket 实时事件，只做快照。
6. 用户端首版不返回完整出价记录，只返回当前最高价、下一口出价金额、出价次数和当前领先用户。
7. 完整出价记录保留给商家后台、审计或后续专门页面；mobile-user 首版不在直播主屏展示历史出价列表。

## 九、直播间竞拍记录接口

### 9.1 接口定义

```text
GET /api/user/live/rooms/{room_id}/auction-records?page=1&page_size=20
```

### 9.2 业务规则

1. 返回当前直播间本次开播以来的竞拍列表，用于前端展示“本场竞拍记录”，不能依赖本地 WebSocket 事件临时拼接。
2. api-gateway 先查询直播间详情，读取 `actual_start_time` 作为本次开播会话起点，再调用 auction-service 按 `room_id` 和 `started_after` 查询竞拍列表。
3. 对竞拍中、已成交、已流拍、已取消记录，auction-service 按 `start_time`、`end_time` 或 `created_at` 命中本次会话的竞拍记录，避免漏掉开播前已创建但开播后才开始或结束的竞拍。
4. 对待开始竞拍，用户侧只返回 `start_time` 在当前服务时间未来 1 小时内的记录；`start_time` 为空、已过期或超过 1 小时的待开始竞拍不返回。
5. 列表按 `created_at DESC, id DESC` 返回，最新创建的竞拍在前。
6. 每条记录包含竞拍基础字段、状态、当前价、成交价、出价次数、领先用户和商品基础快照。
7. api-gateway 需要根据竞拍列表中的 `goods_id` 批量查询 goods-service，并在每条记录中回填 `goods` 对象，避免用户端再额外请求 `/api/goods/batch`。如果某个商品快照查询不到，该条记录仍返回，`goods` 可为空。
8. 该接口不返回完整出价明细；单个竞拍的出价明细仍使用 `GET /api/auctions/{auction_id}/bids`。

```json

  "code": 0,
  "message": "ok",
  "data": {
    "room_id": 500000000001,
    "total": 2,
    "page": 1,
    "page_size": 20,
    "list": [
      {
        "auction_id": 200000000002,
        "room_id": 500000000001,
        "goods_id": 100000000002,
        "status": 2,
        "status_text": "已成交",
```

## 十、建议新增的内部能力

为了让用户端聚合接口更干净，建议补充以下内部 gRPC 能力。

### 10.0 首版实际缺口

对照当前 proto 和网关能力，首版聚合接口主要缺以下内部能力：

| 能力 | 当前情况 | 建议 |
| --- | --- | --- |
| 用户侧播放信息 | `live-service.GetLiveStreamInfo` 第一版不做商家认证，会返回内部流信息 | 网关必须严格过滤字段；后续再拆用户播放方法 |
| 按直播间查询当前竞拍 | 当前主要支持按竞拍 ID、商品 ID 查询 | 新增 `GetCurrentAuctionByRoom` |
| 按多个直播间批量查询当前竞拍 | 首页 feed 会出现一页多个直播间 | 新增 `BatchGetCurrentAuctionsByRoom`，避免 N+1 |
| 批量查询商品 | 已有 `goods-service.BatchGetGoods` | 可直接使用 |
| 批量查询公开商铺 | 当前只有 `GetShop` | 新增 `BatchGetPublicShops`，避免 N+1 |
| 批量查询公开用户 | 当前只有 `GetUser` | 后续可新增 `BatchGetPublicUsers`，首版领先用户用脱敏展示名 |

### 10.1 live-service 用户侧播放信息

当前 `GetLiveStreamInfo` 第一版作为内部通用流信息查询，不在 live-service 层做商家认证和归属校验。用户侧接口必须由 `api-gateway` 严格过滤字段，只返回播放需要的信息。后续可新增：

```text
GetUserLivePlayInfo(room_id)
```

只返回：

- `room_id`
- `webrtc_play_url`
- `media_stream_status`
- 可选兜底播放地址

不返回：

- `stream_name`
- `rtmp_push_url`
- `stream_code`
- 推流密钥

### 10.2 auction-service 按直播间查询当前竞拍

用户端房间态以直播间为入口，而不是以商品或竞拍 ID 为入口。建议新增：

```text
GetCurrentAuctionByRoom(room_id)
```

查询规则：

- 优先返回 `status = 1` 竞拍中的竞拍。
- 如果没有竞拍中，可按业务需要返回最近一个 `status = 0` 待开始竞拍。
- 已成交、已流拍、已取消是否返回，由前端展示需求决定；首版建议只返回待开始或竞拍中。

### 10.3 auction-service 批量按直播间查询当前竞拍

首页 feed 一页会包含多个直播间。如果网关对每个直播间单独调用一次 `GetCurrentAuctionByRoom`，会产生 N+1 查询。建议新增：

```text
BatchGetCurrentAuctionsByRoom(room_ids)
```

返回建议：

```json
{
  "items": [
    {
      "room_id": 500000000001,
      "auction": {}
    }
  ]
}
```

规则：

- `room_ids` 去重后查询。
- 返回结果按 `room_id` 关联，不要求与请求顺序完全一致。
- 没有当前竞拍的直播间可以不返回，也可以返回 `auction = null`；建议不返回，由网关补 `null`。
- 批量接口只返回竞拍摘要，不返回出价记录。

### 10.4 shop-service 批量查询公开商铺信息

首页直播间流一页可能包含多个商铺。建议新增：

```text
BatchGetPublicShops(shop_ids)
```

只返回：

- `shop_id`
- `shop_name`
- `logo`
- `description`
- `status`

不返回：

- 登录账号。
- 手机号。
- 邮箱。
- 审核失败原因。
- 其他内部管理字段。

### 10.5 user-service 批量查询公开用户信息

领先用户展示如果需要昵称和头像，建议后续新增：

```text
BatchGetPublicUsers(user_ids)
```

只返回：

- `user_id`
- `nickname`
- `avatar`

不返回：

- 用户名。
- 手机号。
- 邮箱。
- 生日。
- 地址。
- 登录状态。

第一版可以不依赖该能力，先用 `用户{user_id}` 脱敏展示。

## 十一、错误码建议

| HTTP 状态码 | 场景 | message 建议 |
| --- | --- | --- |
| 400 | 参数格式错误 | 请求参数无效，请检查后重试 |
| 401 | token 无效或过期 | 登录已过期，请重新登录 |
| 403 | 用户状态不允许操作 | 当前账号暂不能参与出价 |
| 404 | 直播间、竞拍或商品不存在 | 内容不存在或已结束 |
| 409 | 业务状态冲突 | 当前状态暂不可操作 |
| 502 | 下游服务不可用 | 服务暂不可用，请稍后重试 |
| 504 | 下游服务超时 | 服务响应超时，请稍后重试 |

## 十二、实现优先级

第一阶段：

1. `GET /api/user/live/feed`
2. `GET /api/user/live/rooms/{room_id}/entry`
3. `GET /api/user/live/rooms/{room_id}/auction-snapshot`
4. `auction-service.GetCurrentAuctionByRoom`
5. 用户侧播放信息字段过滤，确保不返回推流敏感字段

第二阶段：

1. `GET /api/user/live/rooms/{room_id}/preview`
2. `auction-service.BatchGetCurrentAuctionsByRoom`
3. `live-service.GetUserLivePlayInfo`
4. `shop-service.BatchGetPublicShops`

第三阶段：

1. 用户/商铺公开资料批量查询。
2. 在线人数聚合读取。
3. 推荐流 cursor。
4. 用户与直播间关系状态：`previewing`、`entered`、`left`。

## 十三、与 WebSocket 的边界

HTTP 聚合接口负责：

- 首屏数据。
- 快照数据。
- 分页列表。
- 断线重连兜底。

`ws-gateway` 负责：

- 进入直播间后的互动连接。
- 心跳。
- 出价。
- 在线人数变化。
- 竞拍开始、出价成功、成交、流拍、取消等实时事件。

用户出价首版应走 WebSocket：

```text
GET /ws/live?room_id={room_id}&token={access_token}
```

客户端发送：

```json
{
  "type": "place_bid",
  "request_id": "req_bid_1001_30001_1",
  "timestamp": 1780000123000,
  "data": {
    "auction_id": 200000000001,
    "bid_price": 19000
  }
}
```

【废弃说明：2026-06-09，本句“HTTP 聚合接口不设计用户出价入口”已被后续降级方案替代，保留原文供追溯。当前用户端出价推荐优先使用 WebSocket `place_bid`，HTTP `POST /api/auctions/{auction_id}/bids` 仅作为 WebSocket 不可用、重连中或旧客户端兼容时的降级入口。】

## 十四、实现状态

【新增说明：2026-06-07，本段记录首版聚合接口落地情况】

已在 `api-gateway` 实现以下接口：

- `GET /api/user/live/feed`
- `GET /api/user/live/rooms/{room_id}/preview`
- `GET /api/user/live/rooms/{room_id}/entry`
- `GET /api/user/live/rooms/{room_id}/auction-snapshot`
- `GET /api/user/live/rooms/{room_id}/auction-records`

已补充以下下游 gRPC 能力：

- `auction-service.GetCurrentAuctionByRoom`
- `auction-service.BatchGetCurrentAuctionsByRoom`
- `auction-service.ListRoomAuctions`
- `shop-service.BatchGetPublicShops`

当前实现约定：

- 用户侧播放信息仍复用 `live-service.GetLiveStreamInfo`，由 `api-gateway` 过滤字段，不返回 `rtmp_push_url`、`stream_name` 等推流敏感字段。
- `feed` 会聚合直播间、公开商铺、预览播放地址、当前运行中竞拍摘要和商品摘要；在线人数和热度首版返回默认值。
- `entry` 和 `auction-snapshot` 返回当前运行中竞拍；没有运行中竞拍时 `current_auction`、`goods`、`runtime` 为 `null`。
- `auction-records` 返回当前直播间本次开播以来的竞拍列表，按 `actual_start_time` 作为会话起点过滤。
- `viewer` 根据可选用户 token 返回登录态；未带 token 为游客，带 token 但无效由网关返回 `401`。
- `ws.url` 由 `api-gateway` 配置 `userLive.wsUrl` 控制，默认 `/ws/live`；心跳默认 15 秒。
- 领先用户首版不额外查询用户资料，使用 `用户{user_id}` 脱敏展示。
