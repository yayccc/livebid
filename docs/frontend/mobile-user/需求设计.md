# mobile-user 用户端需求设计

## 一、产品定位

`mobile-user` 是 LiveBid 面向普通用户的移动端 H5 应用。第一版核心目标不是做传统电商列表，而是做一个接近 TikTok 体验的直播竞拍浏览和进入流程：

```text
打开首页
 -> 上下滑动浏览直播间
 -> 用户对某个直播间感兴趣
 -> 点击进入直播间
 -> 展示直播、竞拍、商品和实时互动信息
 -> 登录用户可以参与出价
```

第一版要优先保证直播间浏览、进入、播放、竞拍展示和出价链路清晰可用。关注、消息、订单、收藏等能力保留入口，但不阻塞首版。

## 二、页面结构

底部导航保留四个一级入口：

| 页面 | 第一版状态 | 说明 |
| --- | --- | --- |
| 首页 | 实现 | 沉浸式上下滑直播间流 |
| 关注 | 占位 | 后端关注和动态功能未实现，先展示空状态 |
| 消息 | 占位 | 后端私信/通知功能未实现，先展示空状态 |
| 我的 | 实现 | 登录、注册、个人信息、功能入口占位 |

保留四个 Tab 的好处：

- 首版就建立稳定的信息架构。
- 后续补关注、消息、订单、收藏时不需要改变主导航。
- 用户不会误以为产品只有直播广场一个功能。

## 三、首页体验

### 3.1 首页形态

首页采用沉浸式全屏直播间流：

- 每一屏对应一个直播间。
- 用户上下滑切换直播间。
- 当前屏优先展示直播间封面、标题、主播/商铺信息、热度和直播状态。
- 顶部展示半透明搜索入口。
- 底部保留主导航栏。
- 右侧可预留点赞、收藏、分享等纵向操作区，第一版可只展示入口或不实现业务。

首页不采用传统卡片列表作为主体验。列表形态后续可以作为搜索结果页或分类页补充。

### 3.2 直播间预加载

首页首次进入时，从后端加载一批正在直播的直播间：

```text
GET /api/live/rooms?page=1&page_size=10
```

前端保存一个直播间队列，只需要预加载直播间基础信息：

- `live_room_id`
- 标题
- 封面图
- 商铺/主播信息
- 在线人数或热度
- 直播状态
- 播放地址，若列表接口不返回，则在需要时通过详情或 stream 接口获取

滑动预加载规则：

- 当前索引接近队列末尾时，自动请求下一页直播间。
- 建议阈值为距离末尾 2 个直播间以内。
- 当前屏的前一个、当前、后一个直播间允许预渲染 UI。
- 第一版预览态可以直接连接当前直播间播放服务，展示直播画面。

这样可以让滑动体验足够顺，同时避免移动端性能和流量压力过大。

### 3.3 未进入直播间状态

用户刚刷到某个直播间时，直播间处于“预览态”。

预览态展示：

- 优先展示当前直播间的直播画面，可静音自动播放。
- 如果直播流暂不可用，再降级展示直播间封面。
- 直播间标题。
- 主播/商铺名称。
- 热度、在线人数、直播中标识。
- 一个透明灰色的“进入直播间”按钮。

预览态不展示：

- 竞拍面板。
- 商品详情。
- 出价按钮。
- 弹幕列表。
- 完整互动层。
- 竞拍、商品、弹幕等实时事件渲染。

预览态实时连接规则：

- 第一版允许前端在预览态直接连接直播播放服务，展示真实直播画面。
- 如果因为现有后端实现导致预览态也能接收到竞拍、弹幕或系统事件，前端先接收但不渲染这些事件。
- 预览态不主动展示竞拍状态，也不展示商品信息，避免用户误以为已经进入直播间。
- 用户点击“进入直播间”后，前端才切换到房间态并渲染竞拍、商品、弹幕和系统消息。

设计原因：

- 用户刷首页时主要在判断是否感兴趣，不需要被复杂竞拍信息打断。
- 直播画面比静态封面更有吸引力，更接近短视频式浏览体验。
- 进入直播间是明确意图，可以作为渲染竞拍、商品和互动信息的边界。
- 第一版先由前端做预览态事件过滤；后续后端再根据用户与直播间关系限制推送范围。

后续后端优化方向：

- 后端可为用户与直播间关系增加状态，例如 `previewing`、`entered`、`left`。
- `previewing` 状态只允许观看直播流和接收必要的直播状态，不推送竞拍详情、商品详情、弹幕和互动消息。
- `entered` 状态才加入直播间互动分组，推送竞拍、商品、弹幕、系统消息等完整事件。
- 用户切换直播间或离开时，后端及时更新状态并停止对应推送。

### 3.4 进入直播间状态

用户点击“进入直播间”后，当前屏进入“房间态”。

房间态行为：

- 获取直播间详情。
- 获取直播间播放地址。
- 获取当前竞拍信息。
- 获取关联商品信息。
- 建立当前直播间 WebSocket 连接。
- 展示竞拍面板、商品信息、弹幕/系统消息区域和出价按钮。

房间态展示：

- 直播画面。
- 顶部直播间信息。
- 中部弹幕/系统消息。
- 底部左侧商品小卡片，点击后打开商品详情抽屉。
- 右侧中下区域竞拍操作浮层。
- 当前价、加价幅度、倒计时、出价次数、领先用户。
- 出价按钮和登录提示，优先放在右手大拇指容易触达的位置。

退出房间态：

- 用户继续上滑或下滑到其他直播间时，关闭当前直播间 WebSocket。
- 停止当前直播流播放。
- 新直播间恢复为预览态，等待用户点击进入。

第一版同一时间只允许一个直播间处于房间态。

## 四、搜索体验

首页顶部放置搜索栏，但第一版可以先实现 UI 和基础跳转。

搜索入口：

- 固定在首页顶部安全区域内。
- 半透明背景，避免遮挡直播视觉。
- 文案建议为“搜索直播间、主播、商品”。

第一版可选实现：

- 点击进入搜索页。
- 支持输入关键词。
- 如果后端暂无搜索接口，则展示“搜索功能开发中”。

后续搜索接口补齐后，搜索结果可以使用列表卡片，不必使用上下滑直播流。

## 五、竞拍交互

### 5.1 展示信息

房间态竞拍信息分为“商品展示”和“竞拍操作”两块。

商品展示：

- 当前竞拍商品名称和缩略图。
- 商品小卡片默认放在底部左侧。
- 商品详情不在主屏直接铺开，点击商品小卡片后使用底部抽屉展示。
- 商品详情抽屉可展示商品图、商品描述、起拍价、封顶价、商铺信息等。

竞拍操作浮层：

- 出价按钮放在屏幕右侧中下区域，优先贴近右手大拇指自然触达范围。
- 当前价放在出价按钮左侧或上方，用最高视觉优先级展示。
- 倒计时紧邻当前价展示，使用醒目但不刺眼的颜色。
- 当前领先用户放在当前价下方，弱于价格和倒计时。
- 加价幅度、出价次数、竞拍状态放在价格区域附近，以辅助信息展示。

竞拍操作浮层展示：

- 当前最高价。
- 起拍价。
- 加价幅度。
- 封顶价，若有。
- 出价次数。
- 倒计时。
- 当前领先用户。
- 当前状态：待开始、竞拍中、已成交、已流拍、已取消。

布局原则：

- 出价按钮是房间态最高优先级操作，不应被商品详情、弹幕或底部导航遮挡。
- 右侧中下区域优先服务出价操作；点赞、收藏、分享等 TikTok 式操作入口如果存在，应整体上移或弱化。
- 底部导航栏需要保留安全间距，避免用户点击出价时误触导航。
- 具体尺寸、按钮位置和浮层透明度在前端框架搭好后再根据真机手感调整。

### 5.2 出价规则

前端不做最终业务判定，只做基础输入约束和交互提示：

- 游客点击出价时，引导登录。
- 未开始、已成交、已流拍、已取消时禁用出价。
- 出价按钮金额默认使用 `current_price + bid_increment`。
- 提交出价时按钮进入 loading 状态。
- 出价结果以 WebSocket response 和后续广播为准。

WebSocket 出价消息：

```json
{
  "type": "place_bid",
  "request_id": "req_bid_1001_9001_1",
  "timestamp": 1780000123000,
  "data": {
    "auction_id": 1001,
    "bid_price": 15000
  }
}
```

### 5.3 实时事件

房间态需要处理的 WebSocket 事件：

- `room_online_changed`
- `auction_started`
- `bid_accepted`
- `auction_deal`
- `auction_failed`
- `response`

第一版可以先重点处理：

- 在线人数变化。
- 竞拍开始。
- 出价成功。
- 成交或流拍。

## 六、我的页

我的页第一版实现用户基础能力：

未登录状态：

- 登录入口。
- 注册入口。
- 简短说明用户登录后可参与出价。

已登录状态：

- 头像。
- 昵称。
- 用户名。
- 手机号/邮箱，若有。
- 编辑资料入口，按后端实现情况决定是否开放。

功能入口：

- 我的订单，占位。
- 我的竞拍，占位。
- 收藏竞拍，占位。
- 收货地址，占位。
- 设置，占位。

## 八、技术栈建议

结论：建议使用移动端 UI 框架，但不要把 UI 框架当成首页沉浸体验的主要来源。UI 框架负责通用控件效率和一致性，TikTok 式首页体验主要由滑动容器、视频/封面层、半透明叠层、手势状态和业务组件共同完成。

### 8.1 基础技术栈

沿用当前项目基础：

- React
- TypeScript
- Vite
- ESLint

建议新增：

- React Router：页面路由和 Tab 路由。
- Zustand：用户登录状态、token、直播间队列、当前房间状态。
- TanStack Query：服务端数据请求、缓存、分页和重试。
- Swiper：实现首页上下滑全屏直播间流。
- Ant Design Mobile：通用移动端 UI 组件。

### 8.2 UI 框架选择

UI 框架可以提高通用界面的效率，比如：

- 登录表单。
- 弹窗。
- Toast。
- Loading。
- Empty 空状态。
- Sheet/Popup。
- Tabs。
- Input。
- Button。

但首页沉浸式直播流、透明叠层、竞拍面板和直播互动区仍需要业务自定义样式。UI 框架不能完全替代核心体验设计。

选型原则：

- 通用控件交给 UI 框架。
- 首页直播流、房间叠层、竞拍面板使用自定义组件。
- 视觉上以深色沉浸、半透明叠层、清晰价格行动区为主，不直接套后台式组件外观。

首选建议：

```text
Ant Design Mobile
```

原因：

- React 生态内使用成本低。
- 移动端基础组件完整。
- 适合登录、表单、弹窗、Toast、空状态等首版需求。
- 视觉可通过 CSS 变量和局部样式调整，不强制做成后台管理风格。

备选：

```text
React Vant
```

React Vant 更接近轻电商移动端风格，但项目维护和团队熟悉度需要再确认。第一版建议优先选择 Ant Design Mobile。

### 8.3 首页滑动方案

首页上下滑直播间流建议使用 Swiper：

- 开启 vertical 方向。
- 每个 slide 高度占满可视区域。
- 监听 active index 变化。
- 接近末尾时加载下一页。
- 切换 slide 时关闭旧直播间连接和播放。

如果后续需要更强的虚拟列表能力，可以再评估自定义虚拟滑动容器。

## 十、接口依赖

### 10.1 当前可依赖接口

直播间列表：

```text
GET /api/live/rooms?page=1&page_size=10
```

直播间详情：

```text
GET /api/live/rooms/{id}
```

直播间播放信息：

```text
GET /api/live/rooms/{id}/stream
```

注意：`live-service.GetLiveStreamInfo` 第一版不做商家认证，会返回内部流信息。用户端不能直接消费该内部结果，必须通过 `api-gateway` 的用户侧播放/预览或入场聚合接口获取播放字段；网关只返回 `webrtc_play_url`、`media_stream_status` 等用户观看所需字段，不返回 `rtmp_push_url`、`stream_name`、`initial_stream_code` 等推流敏感信息。

用户注册：

```text
POST /api/users/register
```

用户登录：

```text
POST /api/users/login
```

用户信息：

```text
GET /api/users/{id}
PUT /api/users/{id}
```

WebSocket：

```text
GET /ws/live?room_id={room_id}&token={access_token}
```

竞拍详情：

```text
GET /api/auctions/{id}
GET /api/auctions/by-goods/{goods_id}
```

### 10.2 建议后端补充的聚合接口

为了减少进入直播间后的多次请求，建议由 `api-gateway` 提供用户侧聚合接口。详细接口规范见：

```text
docs/frontend/mobile-user/聚合接口设计.md
```

首版重点接口包括：

- `GET /api/user/live/feed`
- `GET /api/user/live/rooms/{room_id}/entry`
- `GET /api/user/live/rooms/{room_id}/auction-snapshot`

用户侧聚合接口不应返回推流地址、推流密钥、内部 stream code 等商家侧字段。

## 十一、边界与取舍

第一版做：

- 四 Tab 主导航。
- 首页上下滑直播间流。
- 直播间基础信息预加载。
- 预览态播放当前直播间直播画面。
- 点击进入直播间。
- 进入直播间后建立当前直播间互动 WebSocket 连接。
- 当前直播间竞拍展示和出价。
- 登录、注册、我的资料。
- 关注和消息占位。

第一版不做：

- 多直播间同时播放。
- 多直播间同时互动 WebSocket 连接。
- 关注真实数据。
- 消息真实数据。
- 订单真实数据。
- 收藏真实数据。
- 完整弹幕系统，若后端未实现可先展示系统竞拍消息。
- 复杂推荐算法，列表按后端返回顺序展示。

## 十二、首版验收标准

首页：

- 打开后能加载直播间流。
- 可以上下滑切换直播间。
- 接近末尾时能自动加载下一页。
- 当前直播间预览态能展示直播画面，流不可用时降级展示封面。
- 预览态只展示基础信息和进入按钮，不渲染竞拍、商品、弹幕等互动事件。
- 点击进入后展示直播、竞拍和商品区域。
- 切换到其他直播间时关闭当前播放和互动连接。

竞拍：

- 未登录用户点击出价会引导登录。
- 登录用户可以发送出价消息。
- 能响应出价成功、价格变化、成交或流拍事件。
- 出价 loading、失败、禁用状态明确。

我的：

- 可以登录、注册。
- 登录后能看到基础用户信息。
- 暂未实现功能有明确空状态。

体验：

- 320px 宽度下文本不溢出。
- 底部导航不遮挡主要按钮。
- 搜索栏和叠层不遮挡核心直播内容。
- 网络错误、空列表、加载中都有可见状态。
