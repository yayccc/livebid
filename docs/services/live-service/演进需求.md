# 持久直播间与直播场次演进需求

> Status: proposed
> Authority: 本文负责直播间可访问性、业务开播、媒体推流和互动能力的目标语义与实施顺序。
> Non-authority: 本文不定义 interaction-service 消息字段和 AI 内部处理策略。
> Applies-to: `refactor/interaction-service` 分支后续演进
> Updated-at: 2026-07-17 +08:00

## 一、问题

当前实现把“用户能否发现和进入直播间”“商家是否已经点击开播”“SRS 是否收到视频流”部分绑定在 `status=living` 上：

1. 公开直播列表默认只返回 `living` 房间。
2. 用户进入直播间聚合接口拒绝 `not_live` 房间。
3. WebSocket 连接可配置为只允许 `living` 房间。
4. 用户弹幕始终要求房间处于 `living`。

这会使已经创建的直播间在未开播时无法形成稳定入口，也无法支持“主播暂未开播但用户仍可进入和互动”的产品体验。

## 二、目标模型

直播间是长期存在的业务容器，直播场次和媒体连接是它下面的短生命周期资源：

```text
LiveRoom（长期存在）
  room_id
  visibility: draft | published | disabled
  chat_enabled
  live_status: not_live | living
  media_stream_status: offline | online
  current_live_session_id: optional

LiveSession（每次业务开播创建）
  live_session_id
  room_id
  started_at
  ended_at

Media Connection（每次推流连接）
  stream_name
  client_id
  generation
  online/offline
```

字段职责：

| 字段 | 决定什么 | 不决定什么 |
| --- | --- | --- |
| `visibility` | 房间是否可被普通用户发现和进入 | 当前是否正在直播、是否有视频 |
| `chat_enabled` | 房间是否接受公开互动消息 | 当前是否有直播场次 |
| `status` | 商家是否已经开始一次业务直播 | SRS 是否收到推流 |
| `media_stream_status` | 视频流当前是否可播放 | 直播场次是否结束 |
| `current_live_session_id` | 当前直播业务上下文 | 房间本身的长期身份 |

## 三、目标状态组合

| visibility | status | media | 用户行为 |
| --- | --- | --- | --- |
| `published` | `not_live` | `offline` | 可以进入；按 `chat_enabled` 决定能否互动；展示“主播暂未开播” |
| `published` | `living` | `offline` | 可以进入和互动；展示“主播正在准备”或“视频暂时中断” |
| `published` | `living` | `online` | 正常播放、竞拍和互动 |
| `published` | `not_live` | `online` | 非法组合；SRS `on_publish` 应拒绝 |
| `draft/disabled` | 任意 | 任意 | 普通用户不可进入；商家管理端仍可按权限查看 |

## 四、业务流程

### 4.1 创建直播间

第一阶段创建成功后默认：

```text
visibility = published
chat_enabled = true
status = not_live
media_stream_status = offline
current_live_session_id = absent
```

如果后续增加草稿编辑流程，可以由商家显式发布；不能复用 `not_live` 表示草稿。

### 4.2 开始直播

商家调用 `StartLive` 时：

1. 校验房间归属、可见性和当前状态。
2. 生成稳定的 `live_session_id`。
3. 创建直播场次记录。
4. 原子更新 `status=living`、`current_live_session_id` 和 `actual_start_time`。
5. 此时即使 `media_stream_status=offline`，房间也已进入业务直播状态。

重复调用必须返回当前同一个 `live_session_id`，不能创建第二个场次。

### 4.3 SRS 推流回调

`on_publish` 只负责鉴权、递增媒体连接 `generation`、记录当前 `client_id` 并设置 `media_stream_status=online`，不能生成新的 `live_session_id`。OBS 断线重连、网络切换或 SRS 重启仍属于同一次业务直播。

`on_unpublish` 必须比较回调 `client_id` 与当前活动连接；只有匹配时才清空活动连接并设置 `media_stream_status=offline`。旧连接的迟到回调只记审计，不得覆盖新连接状态，也不直接结束直播场次。

### 4.4 结束直播

商家调用 `EndLive` 时：

1. 校验并处理仍在运行的竞拍。
2. 结束当前 `LiveSession`。
3. 原子更新 `status=not_live`、清空 `current_live_session_id`、写入 `actual_end_time`。
4. 房间继续保持 `published`，用户仍可进入；互动是否开放由 `chat_enabled` 决定。

## 五、列表与访问需求

“可以访问”和“出现在正在直播推荐流”必须分开：

1. 公开直播推荐流显式筛选 `visibility=published AND status=living`。
2. 店铺直播间目录可以返回所有 `published` 房间，并展示是否开播。
3. 按 `room_id` 直接进入时只要求房间存在且 `visibility=published`，不要求 `living`。
4. 离线房间的聚合入口返回房间、商铺和媒体状态；当前竞拍允许为空。
5. 客户端根据 `status` 与 `media_stream_status` 分别展示“未开播”“准备中/中断”和“播放中”。

## 六、互动与 AI 需求

1. WebSocket 连接校验房间 `published`，不再以 `living` 作为必要条件。
2. 用户消息准入校验 `chat_enabled`，不再强制要求有效直播场次。
3. `room_id` 始终必填，负责连接、广播、房间序号和短历史。
4. `live_session_id` 仅在存在当前业务场次时附加到互动消息。
5. AI 自动处理默认只消费带有效 `live_session_id` 的真人消息。
6. AI 回写必须匹配当前 `live_session_id`；场次结束或切换后拒绝迟到结果。

## 七、live-service 本地实施步骤

以下 `L0～L4` 只表示 live-service 依赖的落地顺序，不是直播互动业务的 P0/P1/P2。跨服务能力阶段以 `docs/features/live-interaction/实施路线.md` 为唯一权威。

### L0：契约与文档

- 扩展 `LiveRoom`：`visibility`、`chat_enabled`、`current_live_session_id`。
- 扩展 `ListLiveRoomsRequest`：可选 `visibility` 过滤。
- 冻结 `UpdateLiveRoom` 的 `request_id`、可更新字段、`FieldMask`、权限与幂等语义，并在实现前追加到 Proto。
- 明确 `room_id` 与 `live_session_id` 的职责和可选性。

### L1：live-service 数据与状态机

- 为现有房间回填 `visibility=published`、`chat_enabled=true`。
- 增加 `live_session` 表和 `live_room.current_live_session_id`。
- 保存活动推流 `client_id/generation`，迟到 `on_unpublish` 不得覆盖新连接。
- `StartLive/EndLive` 使用事务维护房间和场次。
- SRS 回调继续只维护媒体状态。

### L2：查询与用户入口

- 直播推荐流显式筛选正在直播房间。
- 增加或复用店铺公开房间目录查询。
- 用户进入接口允许 `published + not_live`。
- 离线房间返回空竞拍和不可播放状态，而不是业务错误。

### L3：WebSocket 与互动服务

- WebSocket 允许连接已发布的离线房间。
- interaction-service 按 `chat_enabled` 接受房间级消息。
- `room_seq`、短历史、用户幂等和频控按 `room_id` 维护。
- AI 上下文、冷却、决策和回写幂等按 `live_session_id` 维护。

### L4：前端体验

- 展示离线占位页、准备中/断流状态和正常播放状态。
- 离线房间保留弹幕输入和最近互动消息。
- 首页直播推荐与店铺房间目录使用不同筛选语义。

## 八、迁移和兼容要求

1. Proto 只追加字段，不修改现有字段号和枚举值。
2. 旧客户端忽略新增字段后仍能处理现有直播接口。
3. 在服务端完成数据回填前，`visibility=UNSPECIFIED` 和缺失的 `chat_enabled` 按旧数据处理，不能由客户端自行猜测公开与互动权限。
4. 新客户端不得仅根据 `media_stream_status` 判断业务是否开播。
5. 切换弹幕准入前，必须先保证离线房间入口和 WebSocket 连接链路可用。
