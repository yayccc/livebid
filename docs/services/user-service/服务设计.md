# 服务设计

# 数据库设计

### 用户主表

```SQL
CREATE TABLE user (
    id BIGINT PRIMARY KEY COMMENT '主键ID，采用雪花算法',

    -- 登录信息
    username VARCHAR(64) NOT NULL COMMENT '用户登录账号',
    password_hash VARCHAR(255) NOT NULL COMMENT '密码密文（BCrypt算法）',

    -- 基础信息
    nickname VARCHAR(128) NOT NULL COMMENT '用户昵称',
    avatar VARCHAR(255) COMMENT '用户头像URL',
    gender TINYINT DEFAULT 0 COMMENT '性别：0-未知 1-男 2-女',
    birthday DATE COMMENT '生日',

    -- 联系信息
    phone VARCHAR(20) COMMENT '绑定手机号',
    email VARCHAR(128) COMMENT '邮箱',

    -- 状态控制
    status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态：1-启用 2-禁用 3-封禁',

    -- 通用审计字段
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    is_deleted TINYINT DEFAULT 0 COMMENT '是否删除 0-否 1-是',

    -- 扩展字段
    extra JSON COMMENT '扩展字段',

    -- 索引设计
    UNIQUE KEY uk_username(username),
    UNIQUE KEY uk_phone(phone),
    UNIQUE KEY uk_email(email),
    INDEX idx_status(status)
);
```

### 用户地址表

```SQL
CREATE TABLE user_address (
    id BIGINT PRIMARY KEY COMMENT '主键ID，采用雪花算法',

    user_id BIGINT NOT NULL COMMENT '用户ID',

    receiver_name VARCHAR(64) NOT NULL COMMENT '收货人姓名',

    receiver_phone VARCHAR(20) NOT NULL COMMENT '收货人手机号',

    province VARCHAR(64) NOT NULL COMMENT '省',

    city VARCHAR(64) NOT NULL COMMENT '市',

    district VARCHAR(64) NOT NULL COMMENT '区县',

    detail_address VARCHAR(255) NOT NULL COMMENT '详细地址',

    postal_code VARCHAR(20) DEFAULT NULL COMMENT '邮政编码',

    is_default TINYINT NOT NULL DEFAULT 0 COMMENT '是否默认地址 0-否 1-是',

    -- 通用审计字段
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',

    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

    is_deleted TINYINT DEFAULT 0 COMMENT '是否删除 0-否 1-是',

    -- 扩展字段
    extra JSON COMMENT '扩展字段',

    -- 索引
    INDEX idx_user_id(user_id),
    INDEX idx_user_default(user_id, is_default)
);
```

## 二、接口列表

### 上传头像

上传用户头像图片，返回头像访问 URL。 

- **业务规则**

    - 仅支持图片格式（jpg、jpeg、png、webp）。 

    - 文件大小不能超过指定限制（如 5MB）。 

    - 上传成功后返回头像 URL，前端保存，后续注册或修改用户信息时统一提交到后端

    - 用户服务仅保存头像 URL，不保存图片二进制数据。 

    - 图片实际存储于对象存储（MinIO、OSS、COS、S3 等）。 

- **接口地址**

```Plain Text
POST /api/users/avatar/upload
```

- **请求方式**

```Plain Text
Content-Type: multipart/form-data
```

- **请求参数**

|**参数名**|**类型**|**必须**|**说明**|
|---|---|---|---|
|file|File|是|头像图片文件|

- **请求示例**

```Plain Text

```

- **返回值**

```Plain Text
{
  "code": 0,
  "message": "上传成功",
  "data": {
    "url": "https://cdn.example.com/avatar/10001/avatar.png"
  }
}
```

### 用户注册

用户注册账号 

- **业务规则**

    - `username`、`phone`、`email` 不可重复 

    - 密码需满足最小长度要求（如 6 位以上） 

    - 注册成功后用户状态为 1\-启用 

    - 如果用户没有输入昵称，则生成默认随机昵称，为`用户\_6位随机字母数字`

- **接口地址**

```SQL
POST /api/users/register 
```

- **请求参数示例**

```Plain Text
{
  "username": "user001",
  "password": "123456",
  "nickname": "张三",
  "avatar": "https://cdn.example.com/avatar/10001.png",
  "phone": "13800000000",
  "email": "user@qq.com"
}
```

- **参数说明**： 

|**参数名**|**类型**|**必须**|**说明**|
|---|---|---|---|
|username|string|是|用户登录账号|
|password|string|是|用户密码|
|nickname|string|否|用户昵称|
|avatar|string|否|用户头像 URL|
|phone|string|否|手机号|
|email|string|否|邮箱|

- **返回值示例**： 

```Plain Text
{
  "code": 0,
  "message": "注册成功",
  "data": {
    "userId": 10001
  }
}
```

- **接口地址**

## 待确认问题

【新增说明：2026-05-31，本段根据开发前需求澄清补充，确认前不进入编码】

1. 登录接口返回值写的是 JWT，但 `shop-service` 当前登录实现返回的是随机 opaque token；同时 `docs/04-auth-design.md` 约定使用 `pkg/auth` 签发 HS256 JWT，`access_token` 有效期 7 天。请确认 `user-service` 是否直接负责签发 JWT，并新增 `jwt.secret` / `jwt.issuer` 等配置，还是只返回用户登录校验结果，由 `api-gateway` 统一签发 token。

2. “查询用户信息”按用户 ID 查询，其他资料修改和地址接口要求使用当前登录身份。请确认 gRPC 语义：`GetUser(id)` 是否允许内部服务按任意用户 ID 查询公开资料；`UpdateUser`、地址新增/查询/修改/删除/设默认是否必须从 gRPC metadata `livebid-auth-subject` 读取当前 user_id，并拒绝请求参数中的 user_id。

3. “上传头像”依赖对象存储，但当前文档未说明 MinIO/OSS/COS/S3 配置、文件服务或网关上传职责。按项目规范服务默认 gRPC-only，建议本轮不在 `user-service` 实现 multipart 上传，只在注册/修改资料中保存头像 URL，头像上传留给 `api-gateway` 或后续文件服务。请确认。

4. 需求文档要求记录用户登录日志，但数据库设计未定义 `user_login_log` 表。请确认是否按 `shop_login_log` 风格新增 `user_login_log`，字段包含 `id`、`user_id`、`login_ip`、`user_agent`、`login_time`、`login_result`、`extra`、审计字段和逻辑删除字段。

5. 修改收货地址文档中多数参数标为必填，但“修改已有收货地址”可能需要部分更新。请确认 `UpdateAddress` 是全量更新（必填字段必须全部传入）还是部分更新（proto 使用 `optional` 字段，仅修改传入字段）。建议采用部分更新，风格与 `UpdateShopRequest` 一致。

6. 用户主表名写为 `user`。请确认是否保持该表名，还是为了避免与数据库系统表/关键字混淆改为 `users` 或 `user_account`。若保持 `user`，GORM `TableName()` 将严格返回 `user`。

7. 注册规则要求 `username`、`phone`、`email` 不可重复，但 `phone`、`email` 是非必填字段。请确认空字符串是否允许多个用户重复为空。建议实现时将未填写的 `phone`、`email` 保存为空字符串，并在仓储层只对非空值做重复错误映射；数据库唯一索引对空字符串会冲突，需要额外设计避免。

## 设计补充

【新增说明：2026-05-31，本段根据需求澄清确认结果补充】

1. `user-service` 登录成功后直接使用 `pkg/auth` 签发 HS256 JWT，返回 `access_token` 与 `expires_in`。JWT 有效期遵循 `docs/04-auth-design.md`，默认 7 天；服务配置新增 `jwt.secret`、`jwt.issuer`、`jwt.accessTokenTTLSeconds`。

2. 内部服务允许通过 `GetUser(id)` 按任意用户 ID 查询公开用户资料，不返回 `password_hash` 等敏感字段。修改当前用户资料、地址新增、地址列表、地址详情、地址修改、地址删除和设置默认地址必须从 gRPC metadata `livebid-auth-subject` 读取当前 user_id，不信任前端传入的 user_id。

3. 本阶段不实现头像 multipart 上传接口。`user-service` 仅在注册和修改资料时保存头像 URL；图片上传、对象存储和 CDN URL 生成留给 `api-gateway` 或后续文件服务。

4. 本阶段不新增 `user_login_log` 表，也不实现用户登录日志落库。登录日志需求保留，后续如需要审计能力再补充表结构和仓储实现。

5. 修改收货地址采用部分更新语义，proto 使用 `optional` 字段；仅修改请求中显式传入的字段。若 `is_default` 被设置为 1，则同一事务内将该用户其他地址置为非默认。

6. 用户主表表名保持为 `user`，GORM `TableName()` 返回 `user`。

7. `phone`、`email` 非必填；仓储层仅在非空值时校验唯一性。数据库索引策略调整为普通索引，避免多个空值触发唯一索引冲突；唯一约束由仓储查询和写入前校验承担。
