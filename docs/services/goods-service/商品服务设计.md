# 数据库设计

## 商品表

```SQL
CREATE TABLE goods (
    id BIGINT PRIMARY KEY COMMENT '雪花ID',

    shop_id BIGINT NOT NULL COMMENT '店铺ID',

    title VARCHAR(255) NOT NULL COMMENT '商品标题',

    cover_url VARCHAR(500) DEFAULT NULL COMMENT '商品封面',

    description TEXT COMMENT '商品描述',
    
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',

    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    is_deleted TINYINT DEFAULT 0 COMMENT '是否删除 0-否 1-是' ,
    status TINYINT NOT NULL DEFAULT 0 COMMENT '商品状态 0-下架 1-上架'

    KEY idx_shop_id (shop_id)

) ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_unicode_ci
COMMENT='商品表';
```

## 二、接口列表

### 上传商品封面

单独上传商品的封面，返回该文件在服务端保存的URL，用于创建或修改商品时持久化到数据库

- 接口地址

```Plain Text
POST /api/goods/cover/upload
```

- 请求体格式

```Plain Text
Content-Type: multipart/form-data
```

- 参数说明

|**参数名**|**类型**|**必须**|**说明**|
|---|---|---|---|
|file|file|是|商品封面图片|

- 返回值

```JSON
{
  "code": 0,
  "message": "success",
  "data": {
    "cover_url": "https://example.com/goods/cover/xxx.jpg"
  }
}
```

### 创建商品

商铺创建新的商品基础信息。商品创建后归属于当前登录商铺，后续可用于直播间挂品、竞拍活动创建、订单生成等业务。

- 接口地址

```Plain Text

```

- 请求参数示例

```Plain Text

  "cover_url": "https://example.com/image.jpg",
```

|**参数名**|**类型**|**必须**|**说明**|

## 设计补充

【新增说明：2026-05-25，本段根据当前实现、shop-service 项目规范和需求澄清补充】

1. 当前 goods-service 按内部 gRPC-only 服务实现，不直接启动 Gin/HTTP REST。本文档中的 HTTP 接口、基础路径 `/api/goods`、统一返回结构和 multipart 上传格式，暂作为 api-gateway 或后续接入层的外部接口参考，不直接映射为 goods-service 内部启动的 HTTP 路由。
2. 内部 proto 路径为 `api/proto/goods/v1/goods.proto`，生成代码路径为 `gen/proto/goods/v1`，Go package 为 `github.com/yayccc/livebid/gen/proto/goods/v1;goodsv1`。
3. 当前内部 gRPC 方法覆盖：创建商品、编辑商品、删除商品、查询商品详情、分页查询商品列表、查询店铺商品列表、批量查询商品、商品上架、商品下架。
4. 当前数据库实现表名为 `goods`，字段包括 `id`、`shop_id`、`title`、`cover_url`、`description`、`status`、`created_at`、`updated_at`、`is_deleted`。`status` 取值为 `0` 下架、`1` 上架；`is_deleted` 为逻辑删除标记。
5. 原建表 SQL 中 `status` 字段定义后缺少逗号，导致紧跟 `KEY idx_shop_id (shop_id)` 时 SQL 无法直接执行；实际实现通过 GORM AutoMigrate 建表。若后续维护手写 SQL，应在 `status` 字段后补逗号，并保留 `idx_shop_id` 索引。
6. 当前实现额外为 `status` 和 `is_deleted` 建索引，用于列表过滤；这不改变现有业务语义。
7. 当前请求校验：`shop_id`、`id` 必须为正数；`title` 必填且最大 255 字符；`cover_url` 最大 500 字符；分页默认 `page=1`、`page_size=10`，最大 `page_size=100`。
8. 当前错误映射：参数错误返回 gRPC `InvalidArgument`，商品不存在或不属于当前商铺返回 `NotFound`，其他未预期错误返回 `Internal`。
9. 当前列表查询默认过滤 `is_deleted=false`；只有内部调用显式传入 `is_deleted` 时才查询对应删除状态。上下架状态默认不过滤，调用方可通过 `status` 参数筛选。
10. 当前批量查询会去重输入 ID，并按输入 ID 顺序返回已找到且未删除的商品；不存在或已删除的 ID 不会出现在返回列表中。

【新增说明：2026-05-25，本段根据需求确认补充】

1. `category_id` 已确认完全取消，当前建表 SQL、GORM model、proto、handler、repository、README 和测试均不需要增加分类字段。
2. `/api/goods/cover/upload` 已确认由 api-gateway 承接。当前 gateway 只做占位实现：校验 multipart 中存在 `file` 且大小不超过 10MiB，返回假 URL，不进行图片存储、不调用对象存储或 file-service。
3. `shop_id` 已确认后续由鉴权后的 api-gateway 注入；当前注入方案未定，gateway 上传占位接口先使用假 `shop_id=10001` 并在代码保留 TODO。
4. goods-service 查询语义已确认为内部基础数据语义：默认过滤 `is_deleted=false`，不默认过滤 `status`；需要仅查询上架商品时由调用方传入 `status=1` 或在调用方检查返回状态。
5. 删除、编辑、上下架不在 goods-service 内部调用 live/auction/order 服务做引用阻断；相关服务在创建或状态流转时查询商品状态并自行约束。
6. 批量查询已确认返回已找到且未删除的商品列表，部分 ID 缺失不导致整体失败，也暂不返回缺失 ID 列表。

4. 前台展示、直播挂载、竞拍创建、订单生成调用 goods-service 时，是否必须在 goods-service 层强制校验 `status=1` 且 `is_deleted=0`，还是由调用方基于返回的状态自行校验。

6. 批量查询是否需要返回缺失 ID 或对部分缺失整体失败；当前实现返回已找到列表。
