# 商品服务

### 需求分析

针对直播竞拍平台中的商品管理需求，构建统一的商品基础管理服务体系，实现商品从创建、维护、查询到上下架管理的完整业务闭环，并为直播、竞拍、订单等业务模块提供稳定的商品基础数据支撑。

### 核心功能

1. 实现商品创建、编辑、删除及基础信息维护功能，支持商铺对商品资料进行统一管理。 

2. 提供商品列表查询、商品详情查询及商品展示能力，为直播间挂品、竞拍活动和订单生成提供商品基础信息。 

3. 支持商品上下架状态管理，控制商品是否可被展示、挂载或参与后续业务流程。 

4. 维护商品与商铺之间的归属关系，确保商品数据按照商铺维度进行隔离和管理。



## 需求补充

【新增说明：2026-05-25，本段根据当前实现与 shop-service 项目规范补充】

1. goods-service 当前定位为内部商品基础数据 gRPC 服务，默认不直接承接 HTTP REST、multipart 上传、登录态解析或网关层响应格式封装。
2. HTTP 路径、HTTP 动词、统一响应结构与当前登录商铺识别，优先由 api-gateway 或后续接入层承接，再调用 goods-service 的 gRPC 接口。
3. 商品创建默认状态为下架，避免资料未完善的商品直接进入展示、直播挂载或竞拍流程。
4. 商品删除采用逻辑删除，默认查询仅返回未删除商品；是否允许管理端查询已删除商品由调用方通过内部 gRPC 查询参数控制。
5. 分页默认采用 page=1、page_size=10，page_size 最大值暂按 100 处理。

【新增说明：2026-05-25，本段根据需求确认补充】

1. 本期完全取消 `category_id`，goods-service 不维护商品分类字段、分类索引、分类过滤或分类服务依赖。
2. 商品封面上传由 api-gateway 承接，占位阶段只接收 multipart `file` 并返回假 URL，不进行图片存储；goods-service 只保存创建或编辑商品时传入的 `cover_url`。
3. `shop_id` 后续由鉴权后的 api-gateway 注入；在鉴权注入方案未最终确定前，gateway 可先使用假 `shop_id` 并在代码中保留 TODO，goods-service 仍按传入的 `shop_id` 做数据隔离。
4. goods-service 作为内部基础数据服务，默认只过滤逻辑删除，不默认过滤上下架状态；前台展示、直播挂载、竞拍创建和订单生成由调用方按业务场景传入或检查 `status`。
5. 商品是否已被直播、竞拍或订单引用，本期不由 goods-service 跨服务阻断；live/auction/order 等服务在创建或状态流转时自行查询商品状态并约束。
6. 批量查询保持返回已找到且未删除的商品，部分 ID 不存在或已删除时不整体失败。

## 待确认问题

【新增说明：2026-05-25，本段记录会影响 proto、数据库表、核心业务规则或跨服务边界的待确认问题，确认前不作为最终业务规则】

【废弃说明：2026-05-25，下列待确认问题已由用户在本轮回复中确认，保留原文供追溯；最终结论见上方“根据需求确认补充”段落】

1. 商品分类：设计文档的“编辑商品”请求参数出现 `category_id`，但需求、建表 SQL、返回值、proto 与现有代码均没有分类字段。请确认是否需要商品分类能力。推荐方案：本期不纳入 goods-service，先将 `category_id` 视为文档遗留项；若需要分类，则需补充 `category_id` 字段、索引、proto 字段、创建/编辑/列表过滤规则以及分类服务或分类字典来源。
2. 商品封面上传：设计文档包含 `/api/goods/cover/upload` multipart 接口，但当前服务按项目规范保持 gRPC-only，且文档未说明本地文件、对象存储、文件服务、鉴权、大小限制、格式限制和失败处理。请确认封面上传是否由 api-gateway 或独立 file-service 处理，并让 goods-service 只保存 `cover_url`。推荐方案：本期 goods-service 不实现上传。
3. 商铺身份与权限：创建、编辑、删除、上下架均要求“当前登录商铺”或“当前商铺拥有的商品”，但文档未明确登录态来源、JWT 解析位置、网关注入字段以及 goods-service 是否需要调用 shop-service 校验 `shop_id`。推荐方案：由 api-gateway 鉴权并注入可信 `shop_id`，goods-service 仅按 `shop_id` 做数据隔离，不直接校验 JWT 或调用 shop-service。
4. 商品可见性：详情、批量查询、分页查询是否默认返回下架商品需要确认。当前更适合作为内部基础数据服务：默认过滤逻辑删除，不默认过滤上下架状态；前台展示、直播挂载和竞拍创建由调用方传入或检查上架状态。请确认是否要在 goods-service 层强制限制前台语义。
5. 删除/下架与直播、竞拍、订单的关系：需求提到商品会被直播、竞拍、订单使用，但未说明已挂载直播间、已创建竞拍、已有订单的商品是否允许删除、编辑或下架，也未定义需要调用哪个服务校验。推荐方案：goods-service 只维护基础状态；直播、竞拍、订单服务在创建或流转时查询商品状态并自行约束。若需 goods-service 阻止操作，需要补充跨服务调用或事件机制。
6. 批量查询缺失 ID 的语义：当前更保守的内部接口语义是返回已找到的未删除商品，不因部分 ID 不存在而整体失败。请确认是否需要返回缺失 ID 列表或遇到缺失时直接报错。
