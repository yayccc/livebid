# 数据库设计

### 竞拍表

```SQL
CREATE TABLE auction (
    id BIGINT PRIMARY KEY COMMENT '雪花算法生成',

    goods_id BIGINT NOT NULL COMMENT '商品ID',

    shop_id BIGINT NOT NULL COMMENT '店铺ID，冗余字段，方便商家查询',

    start_price BIGINT NOT NULL COMMENT '起拍价，单位: 分',

    bid_increment BIGINT NOT NULL COMMENT '加价幅度，单位: 分'

    seal_price BIGINT DEFAULT NULL COMMENT '封顶价，单位: 分'

    current_price BIGINT NOT NULL COMMENT '当前价格，单位: 分'

    deal_price BIGINT DEFAULT NULL COMMENT '成交价，单位: 分'

    bid_count INT NOT NULL DEFAULT 0 COMMENT '出价次数',

    status TINYINT NOT NULL DEFAULT 0 COMMENT '
    0 待开始
    1 竞拍中
    2 已成交
    3 已流拍
    4 已取消
    ',

    start_time DATETIME DEFAULT NULL COMMENT '竞拍开始时间',

    end_time DATETIME DEFAULT NULL COMMENT '竞拍结束时间',

    winner_user_id BIGINT DEFAULT NULL COMMENT '获胜用户ID',

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',

    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

    is_delete TINYINT NOT NULL DEFAULT 0 COMMENT '0未删除 1已删除',
    version BIGINT NOT NULL DEFAULT 0 COMMENT '版本号',
    UNIQUE KEY uk_goods_id (goods_id),

    KEY idx_shop_id (shop_id),

    KEY idx_goods_id (goods_id),

    KEY idx_status (status),

    KEY idx_shop_status (shop_id, status),

    KEY idx_start_time (start_time),

    KEY idx_end_time (end_time),

    KEY idx_is_delete (is_delete)

) ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_unicode_ci
COMMENT='竞拍表';
```

## 三、Grpc

#### 用户出价

用户对正在进行中的竞拍活动出价。服务需要校验竞拍状态、出价金额、加价幅度、封顶价等规则。

- RPC方法

```Plain Text
// RPC 方法名称: PlaceBid
rpc PlaceBid(PlaceBidRequest) returns (PlaceBidResponse);
```

- 请求消息

```Plain Text
message PlaceBidRequest {
    int64 id = 1;          // 竞拍ID
    int64 user_id = 2;     // 用户ID
    int64 bid_price = 1; // 用户出价金额，单位: 分
}
```

|**参数名**|**类型**|**必须**|**说明**|
|---|---|---|---|
|bid\_price|int64|是|用户出价金额,单位: 分|
|id|int64|是|竞拍ID|
|user\_id|int64|是|出价用户ID|

- 校验规则 

|**校验项**|**说明**|
|---|---|
|状态校验|只有 1 竞拍中 可以出价|
|时间校验|当前时间必须在开始时间和结束时间之间|
|金额校验|出价必须大于当前价格|
|加价校验|出价金额至少为 current\_price \+ bid\_increment|
|封顶价校验|如果设置了 seal\_price，出价不能超过封顶价|

- 响应消息

```Plain Text
message PlaceBidResponse {
    int32 code = 1;            // 状态码，0表示成功
    string message = 2;        // 返回信息
    bool data = 3;             // 是否出价成功
    int64 current_price = 4;  // 当前最新价格，单位：分
}
```

## Redis实时状态管理

- 为保障操作原子性，所有多步的校验与更新操作，均通过Lua脚本完成

在手动开始竞拍时，将竞拍数据加载到Redis中。在Redis中直接管理竞拍状态，通过RocketMQ等消息中间件异步同步到数据库。

## 竞拍数据异步同步

出价校验成功后，通过 RocketMQ 将出价记录和竞拍状态异步同步到数据库中

### Topic

```Plain Text
auction_event
```

### Tag（事件类型）

```Plain Text
auction_started      # 竞拍开始
bid_accepted         # 出价成功
auction_finished     # 竞拍结束（已成交）
auction_failed       # 竞拍流拍
auction_cancelled    # 竞拍取消
```

- 通过 Tag 区分事件类型。 

- 消费端根据 Tag 做不同业务处理。 

### Message Key

```Plain Text
Key = auction_{auction_id}
```

- 用于消息查询、业务追踪。 

- 同一个竞拍活动的消息 Key 一致，便于排查问题。 

- 可以根据需要附加用户 ID，例如 `auction\_\{auction\_id\}\_user\_\{user\_id\}`。

### 顺序性保障

生产者基于auction\_id 将同一个竞拍活动的消息发送到同一个队列中，消费者端采用顺序消费，同一个 MessageQueue 内单线程顺序处理。

### 消息体结构

```Plain Text
{
  "event_id": "evt_10000001",   // 消息唯一ID，用于幂等
  "event_type": "bid_accepted", // 事件类型
  "biz_id": "1001",             // 业务ID，通常是 auction_id
  "auction_id": 1001,
  "room_id": 5001,              // 直播间ID
  "shop_id": 3001,
  "version": 8,                 // 竞拍状态版本号，防止旧消息覆盖新状态
  "timestamp": 1780000000,
  "data": {
    // bid_accepted 事件示例
    "bid_record_id": 7001, //由出价服务在 Redis 更新成功后生成雪花ID，直接作为主键插入日志表中
    "user_id": 9001,
    "bid_price": 15000,
    "bid_time": 1780000123,
    "current_price": 15000,
    "bid_count": 8,
    "winner_user_id": 9001,
    "request_id": "req_abc123"
  }
}
```

### 幂等性保障

- 对于竞拍表，通过 version 判断是否应用该消息，防止旧消息覆盖新状态，保障状态正确性。

```Plain Text
UPDATE auction
SET current_price = ?,
    bid_count = ?,
    winner_user_id = ?,
    version = ?
WHERE id = ?
  AND version < ?;
```

- 对于出价记录表，使用服务端直接生成的主键ID`bid\_record\_id`保障幂等性

# 倒计时

在竞拍主状态中额外维护一个 `expire\_at` 字段，记录竞拍过期时间，每次有人成功出价，则刷新该竞拍的`expire\_at`\(延时\)

- Key

```Plain Text
auction:{auction_id}:state
```

- 出价成功时，向前端广播时要带上服务器更新时间，前端通过`expire\_at \- server\_time`可以较为精确的统计倒计时

## 延迟消息主动检查

每次出价成功后使用 `RocketMQ`发送一条延迟 15 秒的消息：

```Plain Text
{
  "auction_id": 1001,
  "version": 5,
  "expire_at": 1710000015000
}
```

15秒后消费者处理消息，检查：

```Plain Text
Redis 中当前 version 是否还是 5？
Redis 中当前 expire_at 是否 <= now？
Redis 中 status 是否还是竞拍中？
```

如果都满足，说明 15 秒内没人再次出价，直接成交；否则直接丢弃消息。

## 待确认问题

【新增说明：2026-05-29，本段根据开发前需求澄清补充】

1. 本服务是否保持与项目约定一致的 gRPC-only？当前接口文档主要按 HTTP REST 描述，但 `shop-service` 与本轮要求默认 gRPC-only。建议本期将 HTTP 路径、通用返回格式、认证注入等视为 `api-gateway` 职责，`auction-service` 只提供内部 gRPC 方法。

## 设计补充

【新增说明：2026-05-29，本段补充 RocketMQ consumer、幂等、重试和回写策略】

1. `auction-service` 内置 RocketMQ push consumer，消费同一 Topic：`auction_event`。
2. 生产者组：`auction-service-producer`；消费者组：`auction-service-consumer`。
3. consumer 使用集群消费模式（Clustering），同一消息只由消费者组内一个实例处理；消费批量大小为 1，便于单条消息独立重试和幂等记录。
4. consumer 订阅 Tag 表达式为 `*`，由业务代码按 `event_type` 分发：
   - `auction_started`：回写竞拍开始后的状态快照。
   - `bid_accepted`：写入出价记录并回写竞拍当前价、出价次数、获胜用户和版本。
   - `auction_finished`：回写成交状态、成交价、获胜用户和结束时间。
   - `auction_failed`：回写流拍状态和结束时间。
   - `auction_cancelled`：回写取消状态和结束时间。
   - `auction_expire_check`：处理延迟检查消息，原子校验 Redis 中的 `version/status/expire_at` 后决定是否自动结束竞拍。
5. 延迟检查消息使用 `auction_expire_check` 事件类型，消息体至少包含 `auction_id/version/expire_at`。consumer 收到后执行 Redis Lua 原子判断：
   - 当前状态仍为 `1 竞拍中`；
   - 当前 Redis `version` 等于消息版本；
   - 当前 Redis `expire_at` 等于消息中的 `expire_at`；
   - `expire_at <= now`。
   全部满足时自动结束竞拍；有出价则状态改为 `2 已成交`，无出价则状态改为 `3 已流拍`。不满足时直接 ack 丢弃，说明期间已有新出价或状态变化。
6. 数据库增加事件消费幂等表：

```SQL
CREATE TABLE auction_event_consume_log (
    event_id VARCHAR(64) PRIMARY KEY COMMENT '事件唯一ID',
    event_type VARCHAR(64) NOT NULL COMMENT '事件类型',
    biz_id VARCHAR(64) NOT NULL COMMENT '业务ID，通常为auction_id',
    auction_id BIGINT NOT NULL COMMENT '竞拍ID',
    message_id VARCHAR(128) DEFAULT NULL COMMENT 'RocketMQ消息ID',
    status TINYINT NOT NULL DEFAULT 0 COMMENT '0处理中 1成功 2失败',
    retry_times INT NOT NULL DEFAULT 0 COMMENT '重试次数',
    last_error VARCHAR(500) DEFAULT NULL COMMENT '最后一次失败原因',
    consumed_at DATETIME DEFAULT NULL COMMENT '消费成功时间',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    KEY idx_event_type (event_type),
    KEY idx_biz_id (biz_id),
    KEY idx_auction_id (auction_id),
    KEY idx_message_id (message_id),
    KEY idx_status (status)
) ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_unicode_ci
COMMENT='竞拍事件消费幂等表';
```

7. 幂等策略：
   - consumer 处理消息前先写入 `auction_event_consume_log`，以 `event_id` 作为主键。
   - 如果 `event_id` 已成功消费，直接 ack。
   - 如果 `event_id` 正在处理，直接 ack，避免并发重复处理。
   - 如果 `event_id` 上次失败，则更新为处理中并增加 `retry_times` 后重新处理。
   - 出价记录以服务端生成的 `bid_record_id` 作为主键，重复插入视为幂等成功。
   - 竞拍主表以 `version` 做防旧覆盖，只有事件版本大于数据库版本时才应用快照；旧消息视为幂等成功。
8. 重试和死信策略：
   - `maxReconsumeTimes` 默认 5，可通过 `AUCTION_SERVICE_ROCKETMQ_MAX_RECONSUME_TIMES` 配置。
   - 处理失败时标记 `auction_event_consume_log.status=2` 并返回 `ConsumeRetryLater`。
   - 超过最大重试次数后记录失败日志并 ack，由 `auction_event_consume_log` 作为人工排查和补偿依据，避免消息无限重试阻塞消费。
   - 后续如果部署 RocketMQ DLQ 监控，可按消费者组 `auction-service-consumer` 的死信队列接入告警。
