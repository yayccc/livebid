#### 创建竞拍活动

商铺为某个直播间内的商品创建竞拍活动，设置起拍价、加价幅度、封顶价、开始时间和结束时间等规则。

- 业务规则

1. 创建前必须确认商品存在且属于当前商铺；商品不属于当前商铺时创建失败。

2. 创建前必须确认直播间存在且属于当前商铺；直播间不属于当前商铺时创建失败。

【实现说明：2026-06-04】auction-service 创建竞拍时通过 live-service 的 `ValidateLiveRoomForAuction` 校验 `room_id` 归属，当前创建阶段不要求直播间必须处于直播中。

3. 同一个商品只能存在一个未删除的竞拍活动；重复创建同一商品的竞拍活动视为业务失败。

4. 起拍价和加价幅度必须大于 0；设置封顶价时，封顶价不能低于起拍价。

5. 同时设置开始时间和结束时间时，结束时间必须晚于开始时间。

6. 创建成功后竞拍进入 `0 待开始` 状态，当前价等于起拍价，出价次数为 0，暂无获胜用户和成交价。

#### 修改竞拍配置

商铺修改未开始竞拍活动的规则配置。

- 业务规则

1. 只有 `0 待开始` 状态的竞拍活动允许修改配置。

2. `1 竞拍中、2 已成交、3 已流拍、4 已取消` 状态下不允许修改起拍价、加价幅度、封顶价和竞拍时间。

3. 修改起拍价时，当前价会同步重置为新的起拍价；因此该操作只能发生在无人出价的待开始阶段。

4. 起拍价和加价幅度必须大于 0；设置封顶价时，封顶价不能低于当前生效的起拍价。

5. 修改后如果同时存在开始时间和结束时间，结束时间必须晚于开始时间。

6. 修改成功后竞拍仍保持 `0 待开始` 状态，不会自动开始竞拍。

```Plaintext
PUT /api/auctions/{id}
```

#### 开始竞拍

商铺手动开始竞拍，将状态从 `0 待开始` 修改为 `1 竞拍中`。

- 业务规则

1. 只有 `0 待开始` 状态的竞拍活动可以开始。

2. 开始竞拍时，系统先将竞拍数据加载到 Redis 中，此时 status 为 0，此阶段不允许用户出价。

3. Redis 加载成功后，更新数据库状态：

    - status：0 → 1

    - start\_time：服务器实际开始时间

4. 竞拍开始后等待用户首次出价；首次成功出价后启动 15 秒成交倒计时，每次新的成功出价都会重新刷新倒计时。

5. 数据库状态更新成功后，将 Redis 中的 status 从 0 改为 1，此时才允许用户出价。

6. 开始成功后，竞拍正式进入实时竞价阶段，后续出价、倒计时、成交判定均以 Redis 运行态状态为准。

7. 如果数据库状态更新失败，则删除 Redis 中已加载的竞拍数据，并返回开始失败。

8. 非待开始状态的竞拍活动不能再次开始，避免重复加载、重复初始化和状态回退。

9. 开始成功后发送 auction\_started 事件，事件中必须携带直播间 ID，供 WebSocket 服务按直播间广播。

- 接口地址

```Plaintext
POST /api/auctions/{id}/start
```

- 返回值

```Plaintext
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 200000000001,
    "status": 1,
    "start_time": "2026-05-24 20:00:00"
  }
}
```

#### 结束竞拍

商铺手动结束竞拍。系统根据是否存在出价记录决定成交或流拍。

- 业务规则

1. 只有 `1 竞拍中` 状态的竞拍活动可以手动结束。

2. 结束成功后使用服务器当前时间作为实际结束时间。

3. 先修改Redis中的状态，然后将Redis中的状态直接同步到数据库

3. 如果竞拍已有成功出价，则状态流转为 `2 已成交`，当前最高出价用户成为获胜用户，当前价成为成交价。

4. 如果竞拍没有任何成功出价，则状态流转为 `3 已流拍`，获胜用户和成交价为空。

5. 已结束、已取消或未开始的竞拍活动不能通过该接口结束。

6. 结束成功后会产生对应的成交或流拍事件，用于后续订单、通知或状态同步。

- 接口地址

```Plaintext
POST /api/auctions/{id}/finish
```

- 处理逻辑

|**情况**|**结果**|
|---|---|
|有出价记录|状态改为 2 已成交，记录 winner\_user\_id 和 deal\_price|
|无出价记录|状态改为 3 已流拍|

- 返回值：成交

```Plaintext
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 200000000001,
    "status": 2,
    "winner_user_id": 30001,
    "deal_price": 20000,
    "end_time": "2026-05-24 21:00:00"
  }
}
```

- 返回值：流拍

```Plaintext
{
  "code": 0,

    "id": 200000000001,
    "status": 3,
    "winner_user_id": null,

  }
```

#### 取消竞拍

商铺取消未开始或正在进行中的竞拍活动。

- 业务规则

1. `0 待开始` 和 `1 竞拍中` 状态的竞拍活动可以取消。

2. 取消成功后状态流转为 `4 已取消`，结束时间记录为服务器当前时间。

3. 已成交、已流拍、已取消的竞拍活动不能再次取消。

4. 竞拍中取消后，后续不再允许用户继续出价。

5. 取消成功后会产生竞拍取消事件，用于后续通知或状态同步。

- 接口地址

```Plaintext
POST /api/auctions/{id}/cancel
```

- 返回值

```Plaintext
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 200000000001,
    "status": 4
  }
}
```

#### 删除竞拍活动

逻辑删除竞拍活动，仅允许删除未开始、已流拍或已取消的竞拍活动。

- 业务规则

1. 只有 `0 待开始`、`3 已流拍`、`4 已取消` 状态的竞拍活动可以删除。

2. `1 竞拍中` 的竞拍活动不能删除，必须先结束或取消。

3. `2 已成交` 的竞拍活动不能删除，避免影响成交结果和后续订单链路。

4. 删除为逻辑删除，只隐藏竞拍主记录，不删除出价记录。

5. 出价记录保留用于审计和追溯。

- 接口地址

```Plaintext
DELETE /api/auctions/{id}
```

- 返回值

```Plaintext
{
  "code": 0,
  "message": "success",
  "data": true
}
```

## 三、Grpc

#### 用户出价

用户对正在进行中的竞拍活动出价。服务需要校验竞拍状态、出价金额、加价幅度、封顶价等规则。

- 业务规则

1. 只有 `1 竞拍中` 状态且仍在竞拍时间范围内的竞拍活动允许出价。

2. 每次出价必须携带唯一请求标识；重复请求不会形成新的出价，避免用户重复点击或网络重试造成重复竞价。

3. 出价金额必须至少达到 `当前价 \+ 固定加价幅度`。如果设置了封顶价，且 `当前价 + 固定加价幅度` 已经超过封顶价，则允许直接出价到封顶价。

4. 如果竞拍设置了封顶价，出价金额不能超过封顶价；出价等于封顶价是合法出价，但不会立即跳过倒计时直接成交。

5. 当前领先用户不允许连续出价；只有其他用户成功出价成为新的领先用户后，原领先用户才可以再次出价。

6. 出价成功后，本次出价用户成为当前领先用户，当前价更新为本次出价金额，出价次数增加 1。

7. 出价成功会刷新 15 秒成交倒计时，后续自动结束检查以最新倒计时为准。

8. 出价成功会生成出价记录，并发布出价成功事件，用于竞拍状态同步和后续业务处理。

9. 出价失败不会改变当前价、领先用户、出价次数和倒计时。

10. 出价请求必须携带当前直播间 `room_id`，auction-service 需要校验 `auction_id` 与 `room_id` 一致；不一致时拒绝出价。

## 竞拍数据异步同步

出价校验成功后，通过 RocketMQ 将出价记录和竞拍状态异步同步到数据库中

### Consumer、幂等、重试和回写策略

【新增说明：2026\-05\-29，本段补充 RocketMQ consumer、业务幂等、重试和回写策略】

1. `auction\-service` 内置 RocketMQ push consumer，消费同一 Topic：`auction\_event`。

2. 生产者组：`auction\-service\-producer`；消费者组：`auction\-service\-consumer`。

3. consumer 使用集群消费模式（Clustering），同一消息只由消费者组内一个实例处理；消费批量大小为 1，便于单条消息独立重试。

4. consumer 订阅 Tag 表达式为 `\*`，由业务代码按 `event\_type` 分发：

    - `auction\_started`：回写竞拍开始后的状态快照。

    - `bid\_accepted`：写入出价记录并回写竞拍当前价、出价次数、获胜用户和版本。

    - `auction\_finished`：回写成交状态、成交价、获胜用户和结束时间。

    - `auction\_failed`：回写流拍状态和结束时间。

    - `auction\_cancelled`：回写取消状态和结束时间。

    - `auction\_expire\_check`：处理延迟检查消息，原子校验 Redis 中的 `version/status/expire\_at` 后决定是否自动结束竞拍。

5. 延迟检查消息使用 `auction\_expire\_check` 事件类型，消息体至少包含 `auction\_id/room\_id/version/expire\_at`。consumer 收到后执行 Redis Lua 原子判断：

    - 当前状态仍为 `1 竞拍中`；

    - 当前 Redis `version` 等于消息版本；

    - 当前 Redis `expire\_at` 等于消息中的 `expire\_at`；

    - `expire\_at \&lt;= now`。
    全部满足时自动结束竞拍；有出价则状态改为 `2 已成交`，无出价则状态改为 `3 已流拍`。不满足时直接 ack 丢弃，说明期间已有新出价或状态变化。

6. 不新增消息日志表，消息幂等直接由业务表保证：

    - 竞拍主表以 `version` 做防旧覆盖，只有消息版本大于数据库当前版本时才应用快照；如果消息版本小于或等于当前版本，直接丢弃并 ack。

    - 出价记录以服务端生成的 `bid\_record\_id` 作为主键；如果插入失败且属于主键重复，说明消息已处理过，直接丢弃并 ack。

    - 对 `bid\_accepted` 事件，先按 `bid\_record\_id` 尝试写出价记录；如果主键重复则直接丢弃消息，未重复时再按 `version` 尝试更新竞拍主表。

7. 重试和死信策略：

    - `maxReconsumeTimes` 默认 5，可通过 `AUCTION\_SERVICE\_ROCKETMQ\_MAX\_RECONSUME\_TIMES` 配置。

    - 非幂等类业务失败或基础设施异常返回 `ConsumeRetryLater`，由 RocketMQ 触发重试。

    - 超过最大重试次数后记录失败日志并 ack，避免消息无限重试阻塞消费。

    - 后续如果部署 RocketMQ DLQ 监控，可按消费者组 `auction\-service\-consumer` 的死信队列接入告警。

### Tag（事件类型）


### Message Key

```Plaintext
Key = auction_{auction_id}
```

- 用于消息查询、业务追踪。

### 顺序性保障

生产者基于auction\_id 将同一个竞拍活动的消息发送到同一个队列中，消费者端采用顺序消费，同一个 MessageQueue 内单线程顺序处理。

|**字段**|**说明**|

### 幂等性保障

- 对于竞拍表，通过 version 判断是否应用该消息，防止旧消息覆盖新状态，保障状态正确性。

```Plaintext
UPDATE auction
SET current_price = ?,
    bid_count = ?,
    winner_user_id = ?,
    version = ?
WHERE id = ?
  AND version < ?;
```

- 对于出价记录表，使用服务端直接生成的主键ID`bid\_record\_id`保障幂等性；如果插入失败且属于主键重复，说明消息已处理过，直接丢弃并 ack。

# 倒计时

在竞拍主状态中额外维护一个 `expire\_at` 字段，记录竞拍过期时间，每次有人成功出价，则刷新该竞拍的`expire\_at`\(延时\)

- Key

```Plaintext
auction:{auction_id}:state
```

- 出价成功时，向前端广播时要带上服务器更新时间，前端通过`expire\_at \- server\_time`可以较为精确的统计倒计时

## 延迟消息主动检查

每次出价成功后使用 `RocketMQ`发送一条延迟 15 秒的消息：

```Plaintext
{
  "auction_id": 1001,
  "room_id": 4001,
  "version": 5,
  "expire_at": 1710000015000
}
```

15秒后消费者处理消息，检查：

```Plaintext
Redis 中当前 version 是否还是 5？
Redis 中当前 expire_at 是否 <= now？
Redis 中 status 是否还是竞拍中？
```

如果都满足，说明 15 秒内没人再次出价，直接成交；否则直接丢弃消息。
