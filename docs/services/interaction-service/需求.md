# interaction-service 需求

> Status: proposed
> Authority: 本文负责 interaction-service 的服务需求、业务规则和验收。
> Non-authority: 跨服务字段、Redis 和阶段划分由直播互动专题文档负责。
> Depends-on: `docs/services/live-service/演进需求.md`
> Updated-at: 2026-07-17 +08:00

## 一、目标

1. 将弹幕业务真相从 `ws-gateway` 抽离，形成可被 WS、AI 和后续运营生产者复用的统一写入口。
2. 为公开消息提供低延迟准入、短期幂等、基础频控、房间弱顺序和有界最近历史。
3. 向网关提供尽力房间广播，向 AI 提供只关注新鲜真人消息的低延迟输入。
4. 让真人消息和 AI 消息共享身份、安全、序号、历史和广播边界，避免双写和双真相。

详细产品边界见 [直播互动业务边界](../../features/live-interaction/业务边界.md)。

## 二、房间与场次规则

1. 已发布且 `chat_enabled` 的房间允许用户写入，不以 `status=living` 或媒体在线作为必要条件。
2. 用户消息始终属于 `room_id`；房间存在当前业务直播时，由 interaction-service 附加 `live_session_id`。
3. `room_seq`、短历史、用户幂等和用户频控以 `room_id` 为隔离维度。
4. AI 消息必须携带当前 `live_session_id`；场次结束、切换或结果过期时拒绝回写。
5. SRS 推流状态不创建场次，也不决定是否允许房间互动。

房间状态组合与 `StartLive/EndLive` 语义以 [live-service 演进需求](../live-service/演进需求.md) 为准。

## 三、用户消息

`ws-gateway` 代表已认证用户调用统一发布接口。interaction-service 必须：

1. 接收 ws-gateway 已验证并写入 metadata 的终端用户身份；P0 依靠内部网络信任调用方，不实现服务 JWT。
2. 校验房间可访问、互动开启、内容格式和长度。
3. 对同一用户、房间、`request_id` 实现短期幂等。
4. 执行用户级基础频控和最终阻断规则。
5. 生成规范消息、房间序号和服务端时间并写入短历史。
6. 发布房间事件；只有当前业务场次中的真人消息才发布 AI 输入。

昵称由网关在连接级缓存中提供快照；首次缺失时网关可调用 user-service 获取。interaction-service 只做规范化或使用安全兜底值，不在发送链路再次查询用户服务。

## 四、AI 消息

`ai-service` 只能通过助手发布接口回写。interaction-service 必须：

1. 只通过内部拓扑向 `ai-service` 开放该 RPC；P0 暂不做密码学服务身份校验。
2. 重新校验 AI 总开关、room/shop allowlist、当前场次、新鲜度和每房间硬上限。
3. 不信任 AI 传入的发送者、昵称、消息 ID、事件 ID 或房间序号。
4. 对同一场次、`decision_id` 的结果未知重试返回首次消息。
5. 执行长度、空内容和最终阻断词检查后，走与真人消息相同的提交、历史和广播链路。

`decision_id` 只保证一次发布重试的幂等，不能阻止两个 AI 实例独立生成相似回答。

## 五、最近消息

1. 提供按房间查询有界 recent 的内部接口，默认用于进房和重连。
2. 返回结果按 `room_seq` 升序，并返回最新序号与当前可选场次。
3. recent 是展示和轻量补偿，不承诺完整历史、任意翻页或补齐所有序号缺口。
4. 离线房间和跨多次业务场次共用房间短历史；每条消息自身携带可选场次用于展示判断。

## 六、投递与一致性

1. 消息以 Redis 原子提交成功作为业务接纳点；具体 Lua 边界以 [实时分发契约](../../features/live-interaction/contracts/实时分发-v1.md) 为准。
2. 房间广播和 AI 输入均为尽力投递，允许断线期间丢失、重复和乱序。
3. interaction-service 不建设长期消息数据库，也不使用 RocketMQ 补偿实时弹幕。
4. Redis 提交后、Pub/Sub 前崩溃可能使在线客户端漏收；recent 仍可在进入或重连时看到该消息。
5. interaction-service 不可用时，网关不得本地分配消息或先广播。

## 七、安全与权限

1. interaction gRPC 不得对公网或普通客户端开放；普通用户不能直接调用助手发布接口，也不能在请求中自定义 AI 身份。
2. P0 暂时信任内部网关 metadata，这是显式安全欠账，不应在文档或简历中表述为已完成服务认证。
3. AI 自动公开发言必须同时受 ai-service 策略和 interaction-service 最终开关约束。
4. 后续统一增加服务认证时，应通过 interceptor 和 RPC 权限矩阵落地，不修改业务消息或 Handler 主流程。
5. 日志和事件不得泄露用户身份、模型内部推理或业务 Proto 中的隐私字段。
6. 降级和最终安全边界以 [运行与安全](../../features/live-interaction/运行与安全.md) 为准。

## 八、非功能要求

- 服务无本地业务真相，可水平扩展；单房间顺序由 Redis 原子边界保证。
- 依赖超时必须有界，AI 故障不能影响真人消息链路。
- 指标区分用户写入、AI 写入、幂等、频控、状态拒绝、提交和发布失败。
- 新增字段保持向后兼容；正式 Proto 不复用字段号或修改已发布枚举语义。

## 九、P0 验收

1. 发布离线房间消息成功且无 session；开播后消息附加当前 session。
2. 并发重复请求只形成一条消息和一个 `room_seq`，幂等返回完整首次结果。
3. 用户与 AI 消息在同一房间序列和 recent 中展示，请求字段不能自定义发送者身份；P0 内部调用方伪造风险按安全欠账记录。
4. AI 场次错误、过期、禁用或超限时被 interaction-service 拒绝。
5. 多网关实例不需要全量订阅所有房间；订阅与 recent 合并不产生查询窗口漏消息。
6. 关闭或断开 ai-service 后，真人消息仍可正常写入和广播。
7. 切换入口时同一房间不存在 ws-gateway 与 interaction-service 双写。
