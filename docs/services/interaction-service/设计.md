# interaction-service 设计

> Status: proposed
> Authority: 本文负责 interaction-service 内部组件、执行流程、依赖和迁移实现。
> Non-authority: 消息/RPC 与 Redis/频道分别引用共享契约，不在本文复制。
> Updated-at: 2026-07-17 +08:00

## 一、目标结构

```text
ws-gateway                         ai-service
    | PublishUserMessage               | PublishAssistantMessage
    +----------------------+------------+
                           v
                  interaction-service
          auth -> validation -> admission -> commit
                                      |       |
                                      |       +-> room fan-out -> ws-gateway
                                      +----------> AI input -> ai-service
```

服务采用 gRPC-first，不暴露独立 HTTP 写入口。跨服务形状以 [消息与接口契约](../../features/live-interaction/contracts/消息与接口-v1.md) 为准。

## 二、组件

| 组件 | 职责 |
| --- | --- |
| `CallerContextInterceptor` | P0 解析终端 subject 和 trace；为后续服务认证保留统一插入点 |
| `MessageHandler` | 编排用户/AI 发布和 recent 查询 |
| `RoomPolicyClient` | 从 live-service 获取可见性、互动开关和当前场次 |
| `ContentGuard` | 规范化、长度、阻断词和发送者安全校验 |
| `AdmissionRepository` | 执行 Lua 原子提交并返回规范消息 |
| `RoomPublisher` | 发布房间事件 |
| `AIInputPublisher` | 按固定算法发布有效场次真人事件 |
| `FeatureGate` | 全局、shop/room allowlist 和 AI 最终开关 |

Handler 不拼 Redis Key、不自行分配序号；Repository 不调用 live-service 或决定 AI 策略。Publisher 只接受已经提交的事件。

## 三、P0 调用信任模型

P0 暂不实现 service JWT、服务令牌或 mTLS。interaction gRPC 只注册在内部服务网络，不通过公网、Ingress 或 api-gateway 暴露，并依靠部署规则限制调用方为 ws-gateway 与 ai-service。

`CallerContextInterceptor` 负责恢复 trace，并把现有 `pkg/identity` 用户 metadata 转为 `EndUserPrincipal`。该 metadata 在 P0 是受控拓扑下的信任输入，不是密码学认证；任何内部服务获得端口访问权限后理论上都可以伪造，必须记录为安全欠账。

后续统一认证时，在相同 interceptor 链前增加 `ServiceAuthInterceptor`，产生 `CallerService{name}` 并执行 RPC 权限矩阵。Handler 只从 context 读取结果，因此不需要修改 Proto、消息字段或业务流程。

## 四、用户发布流程

1. interceptor 恢复 trace 并解析 ws-gateway 写入的已登录用户 subject；P0 调用方由内部网络拓扑保证。
2. handler 规范化 `request_id`、内容和昵称快照。
3. `RoomPolicyClient` 查询或读取短 TTL 缓存，确认房间 `published + chat_enabled`，取得可选当前 session。
4. `ContentGuard` 执行格式、长度和基础阻断规则。
5. 服务生成消息/事件 ID 与时间，将草稿交给 Repository。
6. Repository 调用共享契约规定的 Lua；幂等命中直接返回首次完整结果。
7. 发布房间事件。首次发布失败时返回 `Unavailable`，调用方可用原 `request_id` 短重试并重发同一事件。
8. 若消息有有效 session 且 AI 输入开关开启，再尽力发布 AI 输入；失败只记指标。
9. 返回规范消息；发送响应与房间事件的网络到达顺序没有保证。

房间状态缓存只用于用户写入并采用很短 TTL；房间不存在、未发布或 `chat_enabled` 不明确时 fail closed。缓存失效不影响已有消息广播。

## 五、AI 发布流程

1. 请求从只对内部 ai-service 开放的调用路径进入；P0 不验证 service JWT。
2. handler 检查 `decision_id`、动作、文本和 `valid_until_ms`。
3. `FeatureGate` 检查全局开关和 room/shop allowlist。
4. `RoomPolicyClient` 直接向 live-service 确认 `status=living` 且当前 session 等于请求值；AI 回写不使用允许陈旧的房间状态缓存。
5. `ContentGuard` 执行最终文本规则，interaction 固定 AI 展示身份。
6. Repository 在同一房间 hash slot 内执行 AI 幂等、硬上限、序号、recent 和结果保存。
7. 发布与用户消息相同的房间事件并返回规范消息。

“结束后拒绝”的判定点是第 4 步校验完成时。与 `EndLive` 并发的在途请求可能成为旧场次最后一条消息；不会被重新标记为新场次。

## 六、recent 与网关订阅

Repository 只返回规范消息实体，不返回 Redis 私有结构。网关进入房间时按 [实时分发契约](../../features/live-interaction/contracts/实时分发-v1.md) 执行“先确认订阅、再查 recent、最后合并去重”。

interaction-service 不持有 WebSocket 连接和本机房间引用计数。网关也不读取 interaction 的 Redis Key，只通过 gRPC 查询 recent、通过 Pub/Sub 接收事件。

昵称仍由网关负责：连接建立后异步预热或首次发送时查询 user-service，并在连接范围缓存。interaction 不做第二次用户查询，避免发送链路多一次依赖。

## 七、失败语义

| 失败点 | 行为 |
| --- | --- |
| 用户身份缺失或无效 | 用户发布返回认证错误，不访问 Redis |
| live-service 不可用 | 新写入返回 `Unavailable`，不使用未知状态放行 |
| Lua 前校验失败 | 返回确定错误，不生成消息 |
| Lua 执行失败 | 返回 `Unavailable`，原幂等键可重试 |
| Lua 成功、房间发布失败 | 返回结果未知/`Unavailable`；重试重发同一事件，可能重复 |
| AI 输入发布失败 | 用户请求仍成功，只记录丢失指标 |
| 进程在提交后崩溃 | 接受实时漏投；recent 保留消息 |

不建立本地写缓冲或第二消息总线兜底，因为它会破坏单一提交点。

## 八、扩展边界

代码从 P0 起定义可替换接口：

- `RoomPolicyProvider`：当前是 live-service gRPC。
- `AdmissionRepository`：当前是 Redis Lua，调用方不感知 Key。
- `EventPublisher`：当前是 Redis Pub/Sub，消息信封不随实现改变。
- `ContentGuard`：当前基础规则，后续可接审核服务。
- `FeatureGate`：当前配置/Redis，后续可接配置中心。

接口提前稳定不等于 P0 部署 Redis Cluster、审核平台或配置中心。

## 九、迁移控制

网关按 room allowlist 使用单一 `interaction_write_mode`：`legacy` 或 `service`。切换步骤：

1. 停止目标房间 legacy 新写入并等待在途请求结束。
2. 清理/迁移 recent 展示边界，不迁移旧序号为新权威序号。
3. 开启 interaction 写入与新频道订阅。
4. 验证后再关闭旧 AI 输入发布和旧 Redis/RocketMQ 配置。

禁止 shadow 双写真实频道；影子验证只能写隔离 Key/频道且不得向客户端或 AI 发布。

## 十、测试重点

- P0 终端 subject 解析、内部端口暴露约束，以及后续服务认证 interceptor 接入点。
- 离线房间、准备中、推流中断、场次结束和切换。
- Lua 并发幂等、频控、序号与 recent 原子性，含 Cluster slot 校验。
- 提交成功但发布超时后的原 ID 重试与客户端去重。
- 多网关动态订阅、recent 竞态和 Redis 重连恢复。
- AI 开关、过期、错误 session、硬上限和最终阻断。
- 迁移开关保证每个房间任一时刻只有一个写入口。
