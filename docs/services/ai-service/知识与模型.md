# ai-service 知识与模型设计

> Status: proposed
> Authority: 本文负责知识路由、业务 Tool、安全投影、缓存、模型边界和 RAG 设计。
> Non-authority: 候选调度与回写见核心设计；启用阶段见统一实施路线。
> Updated-at: 2026-07-17 +08:00

## 一、知识分层

| 层级 | 示例 | 来源 | 是否可缓存自然语言答案 |
| --- | --- | --- | --- |
| 动态事实 | 当前价、出价次数、倒计时、竞拍状态 | 实时业务 Tool | 否 |
| 半静态事实 | 商品标题、规格、起拍价、加价幅度 | Goods/Auction Tool | 仅按版本短缓存事实 |
| 静态知识 | 店铺公开说明、平台规则、商品长文档 | 结构化配置；后续 RAG | 按知识与 Prompt 版本缓存 |
| 会话上下文 | 最近提问、已回答意图 | 当前 SessionAgent | 只在当前 session |

RAG 不能替代动态 Tool；聊天上下文也不能升级为业务权威事实。

## 二、P0 Tool 路由

| 路由 | 调用 | 用途 |
| --- | --- | --- |
| `LIVE_CONTEXT` | `live-service.GetLiveRoom` | 验证 room/shop/current session 等公开上下文 |
| `CURRENT_AUCTION` | `auction-service.GetCurrentAuctionByRoom` | 定位 `auction_id`、`goods_id` 与竞拍配置 |
| `AUCTION_RUNTIME` | `auction-service.GetAuctionRuntime` | 获取当前价、次数、状态、倒计时和版本 |
| `GOODS_PUBLIC` | `goods-service.GetGoods` | 商品标题、公开描述和规格 |
| `SHOP_PUBLIC` | `shop-service.GetShop` | 获取后再投影商家公开展示字段 |

`GetCurrentAuctionByRoom` 返回的持久化 Auction 不能作为当前价格权威；涉及动态状态必须继续读取 Runtime。发布前若生成耗时接近截止时间，重新获取 Runtime 并比较版本/时间，不一致则重生成或放弃。

room/shop allowlist 也使用 `LIVE_CONTEXT` 的同一权威归属，由核心设计中的 `RoomPolicyProvider` 在进入候选前解析并短缓存；模型输入事件中的业务字段不能替代该校验。

## 三、安全投影

每个 Tool adapter 定义专用模型 DTO，只允许最小字段集合。例如：

```text
AuctionFacts{auction_id, status, current_price, bid_count,
             min_increment, remaining_ms, runtime_version, observed_at_ms}
GoodsFacts{goods_id, title, public_description, public_specs, knowledge_version}
ShopFacts{shop_id, display_name, public_notice, knowledge_version}
```

禁止把完整 Proto 直接序列化进 Prompt。必须剔除：胜者/出价用户 ID、手机号、邮箱、地址、内部备注、成本字段、认证材料和未公开商品状态。

Tool 输入参数来自已验证的 room/session 和服务端解析结果，不允许模型或用户直接指定任意 shop、goods、auction ID 越权查询。

## 四、缓存与请求合并

1. 同一决策窗口内相同 Tool 请求可以 singleflight 合并。
2. 半静态事实按实体 ID、业务版本和字段投影版本缓存；失去版本时使用短 TTL。
3. 动态 Runtime 只允许极短请求合并，不缓存最终自然语言答案。
4. 静态答案缓存键至少包含 shop、goods、knowledge version、prompt version、model policy version 和标准化意图。
5. 所有 session 状态和未完成任务按 `live_session_id` 隔离；跨场次只复用有明确版本的静态事实。
6. 缓存未命中或依赖异常不得回退到模型记忆回答动态问题。

## 五、Prompt 与模型接口

Prompt 按职责拆为：固定安全规则、直播公开语气、用户问题、有限场次上下文、Tool 事实和输出 schema。用户文本始终放在数据区，不能拼入系统指令。

`ModelProvider` 输入输出使用内部稳定 DTO，使供应商切换不影响 SessionAgent 和互动 RPC。P0 优先选择支持超时、结构化输出和可控 temperature 的单一模型；模型选择本身不写入跨服务契约。

回答动态事实时要求模型引用内部 `fact_keys`，Guard 再验证实际值来自本次 Tool 结果。模型无法生成合法结构或出现未支持数字时直接拒绝。

## 六、RAG 边界

完整 RAG 不属于 P0。启用时只面向静态或半静态长文本：

```text
source ingest -> parse/chunk -> tenant ACL -> embedding
-> vector retrieval -> metadata/filter -> rerank -> prompt facts
```

每个 chunk 至少带 `shop_id`、可选 `goods_id`、source type、knowledge version、effective time 和权限范围。检索必须先做 tenant/商品过滤，不能跨商家召回。

RAG 结果仍是不完全可信的参考资料：过期、冲突、低相似度或无有效版本时不回答。价格、库存、倒计时、竞拍状态和用户数据永远走实时 Tool。

向量数据库和 Embedding 模型是可替换实现，不得改变消息、RPC、分片或 Tool DTO。

## 七、知识更新

- 商品或商家公开资料变化时增加 `knowledge_version`，旧缓存自然失效。
- RAG 建索引采用新版本就绪后切换 alias，避免半构建索引被在线查询。
- 删除或禁用资料必须触发缓存失效和索引 tombstone。
- 决策审计记录使用的事实版本和检索文档 ID 摘要，不在公开消息传递内部来源。

## 八、验证重点

- 当前价类问题确实调用 Runtime，且旧版本结果不能发布。
- Shop/Runtime 完整 Proto 的隐私字段无法进入模型 DTO。
- 用户不能通过文本诱导 Tool 查询其他房间、商家或用户。
- Tool 超时、空结果和冲突结果都不会回退为编造答案。
- 缓存键包含 tenant、知识和 Prompt 版本，跨场次不复用动态答案。
- RAG 启用后 tenant filter、删除、版本切换和低相关拒答可测试。
