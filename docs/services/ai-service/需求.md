# ai-service 需求

> Status: proposed
> Authority: 本文负责 AI 自动公共问答的业务行为、约束和验收。
> Non-authority: 共享消息、实时分片、运行开关和阶段划分由直播互动专题负责。
> Updated-at: 2026-07-17 +08:00

## 一、定位

ai-service 是直播中的选择性公共问答服务。它持续观察可收到的真人互动，但只对少量高价值、高置信问题生成公开消息，以减少主播重复回答和用户信息查找成本。

服务不追求“每问必答”。低价值闲聊、已有人回答、重复问题、风险问题和超出知识边界的问题都可以不回复。

## 二、用户价值

1. 用户直接在公屏提问，无需学习 `@AI` 或打开私人入口。
2. 一条回答可以同时帮助多名观众，避免相同问题刷屏。
3. AI 身份必须显著区别于真人和主播，用户能够理解回答来源。
4. AI 频率受控，不能抢占直播主体或连续打断主播。
5. 对价格、倒计时和竞拍状态等动态问题，回答必须来自实时业务事实。

## 三、输入要求

1. 只消费 interaction-service 已接纳的真人消息事件。
2. 只处理携带当前有效 `live_session_id` 且未过期的事件。
3. 输入允许丢失、重复和乱序；服务重启后不追补旧消息。
4. 同一场次的上下文、冷却和已回答意图不能复用到下一次开播。
5. AI 输入关闭或房间不在灰度范围时，不创建模型任务。

共享事件和投递语义以 [消息契约](../../features/live-interaction/contracts/消息与接口-v1.md) 和 [实时分发契约](../../features/live-interaction/contracts/实时分发-v1.md) 为准。

## 四、选择性处理

进入模型前必须完成：

1. 过滤空内容、灌水、纯表情、明显广告、无意义重复和过期消息。
2. 在短窗口内聚合同一问题的相似表达，选择代表消息。
3. 识别是否已经被主播、其他用户或 AI 在近期回答。
4. 根据问题价值、可回答性、时效性、重复受益和风险进行候选排序。
5. 受场次冷却、并发任务和模型预算约束，只选择少量候选。

不满足置信度阈值时使用内部 `NO_REPLY`，不向 interaction-service 发布空消息。

## 五、回答能力

首个业务闭环启用两种公开动作：

- `ANSWER`：对商品、商家公开信息、直播流程、竞拍规则和当前竞拍状态作简短回答。
- `REDIRECT`：涉及售后承诺、隐私、支付纠纷、医疗法律或资料不足时，引导咨询主播/客服，不编造结论。

`ATMOSPHERE` 仅作为兼容枚举保留，在接入可靠的直播生命周期和商品事件前不得启用。

回答必须：

1. 简短、口语化、适合公屏，不重复用户隐私和内部数据。
2. 动态事实来自 Tool，不能依赖模型记忆或 RAG 文档中的旧值。
3. 资料缺失、依赖超时或事实冲突时放弃回答或 `REDIRECT`。
4. 在新鲜度内通过 interaction-service 回写，不能直接广播。
5. 关联被回答的代表消息，方便审计和后续重复抑制。

## 六、知识边界

- 商品说明、商家公开资料和平台规则可使用结构化 Tool；完整 RAG 属于后续能力。
- `GetCurrentAuctionByRoom` 只用于定位当前竞拍及配置；当前价、出价次数、倒计时和版本必须读取 `GetAuctionRuntime`。
- Tool 只向模型暴露白名单投影，不传完整 Shop、Goods、AuctionRuntime Proto。
- 缓存不能让动态竞拍事实跨决策窗口复用，也不能让一次直播的上下文污染下一场。

详细来源与缓存边界见 [知识与模型](./知识与模型.md)。

## 七、安全要求

1. 自动公开发言受全局开关、room/shop allowlist、场次冷却和 interaction 最终硬上限共同约束。
2. 用户文本一律视为不可信数据，不能覆盖系统规则、要求泄露 Prompt 或调用未授权工具。
3. 模型输出必须经过结构校验、风险规则和长度检查，不能把自由文本直接发布。
4. AI 回写因禁用、过期或场次不匹配被拒绝后，不得创建新 `decision_id` 绕过。
5. 关键决策必须可审计，但不保存模型思维过程或未脱敏隐私。

完整模型安全与评测见 [安全与评测](./安全与评测.md)，跨服务止损见 [运行与安全](../../features/live-interaction/运行与安全.md)。

## 八、非功能要求

- AI 故障、重启或限额不能影响真人互动。
- 每个场次状态有界，空闲或结束后及时释放。
- 模型和 Tool 调用有明确超时、并发与预算限制。
- 服务具备更换模型、知识实现和调度策略的接口边界。
- 观测覆盖输入丢弃、候选原因、工具失败、模型延迟、动作、发布拒绝和安全拦截。

端到端时延和可用性目标以 [运行与安全](../../features/live-interaction/运行与安全.md) 为准。

## 九、P0 验收

1. 单实例能够消费全部逻辑分片，并按 session 隔离上下文。
2. 大部分普通弹幕在规则与候选阶段结束，不触发模型调用。
3. 相似问题在短窗口内只产生一个候选；冷却期内不重复公开回答。
4. 动态竞拍回答使用 Runtime 实时值，Tool 失败时不猜测。
5. 模型只生成允许的结构化动作；过期、错误 session 和关闭房间无法发布。
6. 同一 `decision_id` 的结果未知重试不产生第二条消息。
7. 停止 ai-service、模型或知识依赖后，真人弹幕指标和可用性不受影响。
8. 离线评测达到项目设定的安全和准确门槛后，才允许 room allowlist 灰度。
