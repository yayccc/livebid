# WebSocket 网关服务

### 需求分析

针对直播竞拍平台中的实时消息需求，构建独立的 WebSocket 网关服务，作为用户端与服务端之间的实时通信入口。ws-gateway 负责维护用户长连接、管理直播间订阅关系、接收用户出价消息并转发给竞拍服务，同时消费竞拍服务产生的事件并按直播间广播给在线用户，支撑直播间内竞拍价格、倒计时、成交结果等信息的实时同步。

ws-gateway 不负责竞拍规则判定、价格更新、成交判定、订单生成或数据库写入。竞拍有效性、当前价、领先用户、30 秒成交倒计时和成交/流拍状态均以 auction-service 为准。

### 核心功能

1. 实现 WebSocket 连接管理能力，支持用户建立连接、断开连接、心跳保活和异常连接清理。

2. 实现直播间订阅能力，用户进入直播间后加入对应 `room_id` 的连接分组，离开直播间或断开连接后从分组中移除。

3. 实现用户实时出价入口，接收客户端出价消息，校验基础消息格式后调用 auction-service 的出价接口；ws-gateway 只负责转发请求和返回结果，不在本地判断加价幅度、封顶价、连续出价或成交状态。

4. 实现竞拍事件广播能力，消费 auction-service 发布的竞拍事件，根据事件中的 `room_id` 将消息广播给对应直播间内的在线用户。

5. 支持广播核心竞拍事件，包括竞拍开始、出价成功、竞拍成交、竞拍流拍和竞拍取消。`auction_expire_check` 属于竞拍服务内部延迟检查事件，不对前端广播。

6. 向前端广播出价成功事件时，需要包含当前价、领先用户、出价次数、竞拍状态、服务器时间和 `expire_at`，便于客户端展示最高价和 30 秒倒计时。

7. 向前端广播成交、流拍或取消事件时，需要包含竞拍 ID、直播间 ID、最终状态、成交价、获胜用户和结束时间，便于直播间及时更新竞拍结果。

8. 提供统一的 WebSocket 消息格式，区分客户端请求、服务端响应和服务端广播，保证用户端可以按消息类型处理连接状态、出价结果和竞拍状态变化。

9. 实现直播间在线人数统计能力，基于 Redis 维护直播间维度的在线用户和连接状态，并在用户进入、离开、断连或心跳超时后更新在线人数。

10. 在线人数默认按去重用户数统计，同一用户在同一直播间打开多个连接只计为 1 人；同时保留连接数统计，用于排查连接压力和异常连接。

11. 在线人数发生变化时，向对应直播间广播最新人数，便于用户端实时展示直播间在线状态。

### 本期边界

1. 本期已包含直播竞拍核心消息链路和直播间文本弹幕一期能力；弹幕范围以 `弹幕功能需求.md` 和 `弹幕功能设计.md` 为准。

2. 本期不实现私聊、礼物、点赞、红包、风控拦截或后台运营指令。

3. 本期不在 ws-gateway 持久化连接消息和竞拍事件；历史出价记录、竞拍详情和订单信息仍由对应业务服务提供查询。

4. 本期不由 ws-gateway 直接读写竞拍数据库或 Redis 竞拍状态；需要竞拍数据时通过 auction-service 接口或 auction-service 事件获取。

5. 本期只按 `room_id` 做直播间维度广播，不做用户标签、人群分层或跨直播间广播。

### 在线人数统计口径

1. 展示口径为直播间去重在线用户数，统计对象为已加入对应 `room_id` 的有效 WebSocket 连接。

2. 同一用户在同一直播间存在多个有效连接时，前端展示人数只增加 1；连接数仍单独记录。

3. 用户主动离开直播间、关闭连接或连接心跳超时后，ws-gateway 需要更新 Redis 中的在线状态。

4. 心跳超时连接需要由 ws-gateway 定期清理，避免用户异常断网后长期占用在线人数。

5. 多实例部署时，各 ws-gateway 实例共享 Redis 在线状态，保证同一直播间的人数统计在全局维度一致。
