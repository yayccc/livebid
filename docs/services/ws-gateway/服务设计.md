# WebSocket 网关服务设计

## 一、服务定位

`ws-gateway` 是直播竞拍业务的实时通信入口，负责用户 WebSocket 长连接、直播间连接分组、出价消息转发、竞拍事件广播和在线人数统计。

`ws-gateway` 不直接修改竞拍数据库，不直接修改 auction-service 的 Redis 竞拍状态，也不做出价金额、加价幅度、封顶价、连续出价或成交规则判定。所有竞拍业务事实以 `auction-service` 为准。

## 二、核心依赖

|依赖|用途|
|---|---|
|WebSocket Server|承接用户端长连接和实时消息收发|
|Redis|维护直播间在线用户、连接状态、在线人数和多实例广播通知|
|RocketMQ|消费 `auction-service` 发布的竞拍事件|
|auction-service gRPC|转发用户实时出价请求|
|live-service gRPC|校验直播间是否存在、是否允许进入|
|JWT/Auth|识别用户身份；观看可按业务策略允许匿名，出价必须登录|

## 三、连接入口

### WebSocket 地址

```Plaintext
GET /ws/live?room_id={room_id}&token={access_token}
```

### 参数说明

|参数|类型|必须|说明|
|---|---|---|---|
|room_id|int64|是|直播间 ID|
|token|string|否|用户端 access token；出价必须携带有效用户 token|

### 连接规则

1. `room_id` 必须大于 0。

2. 建立连接时，ws-gateway 校验直播间存在；建议调用 `live-service` 查询直播间，并优先只允许进入 `living` 状态直播间。

3. `token` 为空时，连接按游客连接处理，只允许观看和接收广播，不允许出价。

4. `token` 存在时，必须是用户端 JWT；校验成功后将连接绑定到 `user_id`。

5. 同一个 WebSocket 连接第一版只绑定一个直播间。用户切换直播间时，关闭旧连接并重新建立新连接。

6. 连接建立成功后，ws-gateway 将连接加入当前 `room_id` 的本地连接分组，并同步更新 Redis 在线状态。

7. 连接断开、主动离开或心跳超时时，ws-gateway 将连接从本地分组和 Redis 在线状态中移除。

## 四、统一消息格式

### 客户端请求

```Plaintext
{
  "type": "place_bid",
  "request_id": "req_10000001",
  "timestamp": 1780000000000,
  "data": {}
}
```

|字段|说明|
|---|---|
|type|消息类型|
|request_id|客户端请求唯一标识，用于响应匹配和出价幂等|
|timestamp|客户端发送时间，Unix 毫秒|
|data|业务数据|

### 服务端响应

```Plaintext
{
  "type": "response",
  "request_id": "req_10000001",
  "code": 0,
  "message": "success",
  "server_time": 1780000001000,
  "data": {}
}
```

|字段|说明|
|---|---|
|type|固定为 `response`|
|request_id|对应客户端请求 ID|
|code|状态码，`0` 表示成功|
|message|响应说明|
|server_time|服务端响应时间，Unix 毫秒|
|data|响应数据|

### 服务端广播

```Plaintext
{
  "type": "bid_accepted",
  "event_id": "evt_10000001",
  "room_id": 4001,
  "auction_id": 1001,
  "server_time": 1780000001000,
  "data": {}
}
```

|字段|说明|
|---|---|
|type|广播事件类型|
|event_id|事件 ID；竞拍事件沿用 auction-service 的 `event_id`|
|room_id|直播间 ID|
|auction_id|竞拍 ID；非竞拍事件可为 0 或省略|
|server_time|服务端广播时间，Unix 毫秒|
|data|广播数据|

### 时间字段约定

WebSocket 对外 JSON 消息中的时间字段统一使用 Unix 毫秒，包括 `timestamp`、`server_time`、`expire_at`、`start_time`、`end_time`、`connected_at`、`last_seen_at` 等。

ws-gateway 消费 auction-service 事件时，如果上游事件中的 `timestamp`、`bid_time` 等字段为 Unix 秒，必须在转换为 WebSocket 消息前统一转换为 Unix 毫秒。配置项中的心跳间隔、超时时间仍使用秒。

## 五、客户端消息

### ping

客户端心跳消息。

```Plaintext
{
  "type": "ping",
  "request_id": "req_ping_1",
  "timestamp": 1780000000000,
  "data": {}
}
```

响应：

```Plaintext
{
  "type": "response",
  "request_id": "req_ping_1",
  "code": 0,
  "message": "pong",
  "server_time": 1780000001000,
  "data": {}
}
```

业务规则：

1. 客户端应按固定周期发送心跳，建议 15 秒一次。

2. ws-gateway 收到心跳后刷新本连接在 Redis 中的过期时间。

3. 如果超过心跳超时时间仍未收到心跳，服务端关闭连接并清理在线状态。

### place_bid

用户通过 WebSocket 发起实时出价。

```Plaintext
{
  "type": "place_bid",
  "request_id": "req_bid_1001_9001_1",
  "timestamp": 1780000123000,
  "data": {
    "auction_id": 1001,
    "bid_price": 15000
  }
}
```

业务规则：

1. 出价必须是已登录用户连接；游客连接发送出价请求时返回未登录错误。

2. `auction_id` 和 `bid_price` 必须大于 0。

3. `request_id` 必须由客户端生成并保证同一次出价重试时保持不变。

4. ws-gateway 使用连接绑定的 `user_id` 调用 auction-service 的 `PlaceBid`，不信任客户端传入的 `user_id`。

5. ws-gateway 不在本地判断出价是否合法；加价幅度、封顶价、连续出价、竞拍状态和 15 秒成交倒计时均由 auction-service 判定。

6. ws-gateway 需要确保该出价发生在当前连接所属直播间内。实现时必须在 `PlaceBid` 请求中传入当前 WebSocket 连接绑定的 `room_id`，由 auction-service 校验 `auction_id` 与 `room_id` 的关系。

7. 出价成功后，ws-gateway 立即向当前连接返回出价结果；面向全直播间的价格更新以 auction-service 后续发布的 `bid_accepted` 事件广播为准。

成功响应示例：

```Plaintext
{
  "type": "response",
  "request_id": "req_bid_1001_9001_1",
  "code": 0,
  "message": "success",
  "server_time": 1780000123000,
  "data": {
    "accepted": true,
    "current_price": 15000,
    "bid_count": 8,
    "winner_user_id": 9001,
    "expire_at": 1780000138000
  }
}
```

失败响应示例：

```Plaintext
{
  "type": "response",
  "request_id": "req_bid_1001_9001_1",
  "code": 409,
  "message": "出价未被接受",
  "server_time": 1780000123000,
  "data": {}
}
```

### room_leave

客户端主动离开直播间。

```Plaintext
{
  "type": "room_leave",
  "request_id": "req_leave_1",
  "timestamp": 1780000200000,
  "data": {}
}
```

业务规则：

1. 服务端收到后清理当前连接在直播间内的订阅关系和 Redis 在线状态。

2. 第一版收到 `room_leave` 后可以直接关闭 WebSocket 连接。

3. 在线人数变化后，向当前直播间广播最新在线人数。

## 七、Redis 在线状态设计

ws-gateway 不使用 MySQL 保存连接状态。在线状态使用 Redis，并通过 Lua 脚本保证进入、心跳、离开和清理的原子性。

### 连接状态

```Plaintext
Key: ws:conn:{connection_id}
Type: Hash
TTL: heartbeat_timeout_seconds * 2
```

字段：

|字段|说明|
|---|---|
|connection_id|连接 ID，服务端生成|
|instance_id|ws-gateway 实例 ID|
|room_id|直播间 ID|
|identity_key|在线统计身份，登录用户为 `u:{user_id}`，游客为 `g:{guest_id}`|
|user_id|登录用户 ID，游客为 0|
|connected_at|连接建立时间，Unix 毫秒|
|last_seen_at|最后心跳时间，Unix 毫秒|
|expire_at|连接过期时间，Unix 毫秒|

### 直播间连接集合

```Plaintext
Key: ws:room:{room_id}:connections
Type: ZSET
Member: connection_id
Score: expire_at
```

用途：

1. 统计直播间连接数。

2. 按 `expire_at` 清理心跳超时连接。

### 直播间用户集合

```Plaintext
Key: ws:room:{room_id}:users
Type: ZSET
Member: identity_key
Score: expire_at
```

用途：

1. 统计直播间去重在线用户数。

2. 同一登录用户多连接只占一个 `identity_key`。

3. 用户存在多个连接时，`expire_at` 取该用户仍有效连接中的最大过期时间。

### 用户连接集合

```Plaintext
Key: ws:room:{room_id}:user:{identity_key}:connections
Type: SET
Member: connection_id
TTL: heartbeat_timeout_seconds * 2
```

用途：

1. 判断某个用户在直播间是否仍有有效连接。

2. 用户断开某个连接时，如果集合中仍有其他有效连接，则在线人数不减少。

3. SET 本身只保存候选 connection_id；判断是否有效时必须回查 `ws:conn:{connection_id}` 是否存在，并校验连接所属 `room_id`、`identity_key` 和 `expire_at > now`。

4. 每次进入、心跳、离开或超时清理后，必须通过 Lua 脚本基于仍有效连接重新计算该 `identity_key` 的最大 `expire_at`，再更新或删除 `ws:room:{room_id}:users`，不能简单用当前连接的 `expire_at` 覆盖用户 ZSET score。

### 在线人数计算

```Plaintext
online_user_count = ZCARD ws:room:{room_id}:users
connection_count = ZCARD ws:room:{room_id}:connections
```

计算前需要先清理已过期连接和过期用户，避免异常断网导致人数长期偏高。

### 用户有效连接重算规则

进入、心跳、离开和超时清理都需要在同一个 Lua 脚本中维护以下不变量：

1. `ws:room:{room_id}:connections` 中只保留仍存在且 `expire_at > now` 的连接。

2. `ws:room:{room_id}:user:{identity_key}:connections` 中只保留仍存在、属于当前直播间、属于当前 `identity_key` 且 `expire_at > now` 的连接。

3. `ws:room:{room_id}:users` 中每个 `identity_key` 的 score 等于该用户所有有效连接中的最大 `expire_at`。

4. 如果某个 `identity_key` 已无有效连接，必须从 `ws:room:{room_id}:users` 中删除。

5. 在线人数和连接数必须在完成上述清理和重算后再读取。

推荐在 Lua 中封装 `recompute_identity(room_id, identity_key, now_ms)` 逻辑：

```Plaintext
1. 遍历 ws:room:{room_id}:user:{identity_key}:connections。
2. 对每个 connection_id 回查 ws:conn:{connection_id}。
3. 如果连接不存在、room_id 不一致、identity_key 不一致或 expire_at <= now_ms，则从用户连接 SET 和房间连接 ZSET 中移除。
4. 对仍有效连接取 max(expire_at)。
5. max_expire_at 存在时，ZADD ws:room:{room_id}:users max_expire_at identity_key。
6. max_expire_at 不存在时，ZREM ws:room:{room_id}:users identity_key，并删除或缩短用户连接 SET 的 TTL。
```

## 八、在线人数流程

### 进入直播间

1. 生成 `connection_id`。

2. 识别连接身份，得到 `identity_key`。

3. 写入 `ws:conn:{connection_id}`。

4. 将连接加入 `ws:room:{room_id}:connections`。

5. 将连接加入 `ws:room:{room_id}:user:{identity_key}:connections`。

6. 调用用户有效连接重算逻辑，按最大 `expire_at` 将用户加入或刷新 `ws:room:{room_id}:users`。

7. 计算最新 `online_user_count` 和 `connection_count`。

8. 发布 `room_online_changed`。

### 心跳刷新

1. 刷新 `ws:conn:{connection_id}` 的 `last_seen_at`、`expire_at` 和 TTL。

2. 刷新 `ws:room:{room_id}:connections` 中当前连接的过期分数。

3. 调用用户有效连接重算逻辑，按该用户仍有效连接中的最大 `expire_at` 刷新 `ws:room:{room_id}:users`，避免旧连接心跳覆盖新连接更晚的过期时间。

4. 心跳刷新通常不广播在线人数，除非清理过期连接后人数发生变化。

### 离开直播间

1. 删除 `ws:conn:{connection_id}`。

2. 从 `ws:room:{room_id}:connections` 删除当前连接。

3. 从 `ws:room:{room_id}:user:{identity_key}:connections` 删除当前连接。

4. 调用用户有效连接重算逻辑；如果该用户无其他有效连接，从 `ws:room:{room_id}:users` 删除当前用户。

5. 计算最新人数并发布 `room_online_changed`。

### 超时清理

1. ws-gateway 定时扫描自己负责的直播间或活跃直播间。

2. 从 `ws:room:{room_id}:connections` 中找出 `expire_at <= now` 的连接。

3. 对每个过期连接执行离开清理逻辑，并对受影响的 `identity_key` 执行用户有效连接重算。

4. 清理后如果在线人数变化，发布 `room_online_changed`。

## 九、多实例广播

### 本地连接管理

每个 ws-gateway 实例只保存本实例上的 WebSocket 连接对象：

```Plaintext
room_id -> connection_id -> connection
```

服务端广播时，只向本实例中属于目标 `room_id` 的连接写消息。

### 在线人数广播

在线人数由 Redis 统一维护。任意实例更新在线人数后，通过 Redis Pub/Sub 发布房间在线人数事件：

```Plaintext
Channel: ws:room:{room_id}:events
```

所有 ws-gateway 实例订阅该频道模式，收到 `room_online_changed` 后向本实例内对应直播间连接广播。

### 竞拍事件广播

ws-gateway 消费 `auction_event` Topic 中的竞拍事件。为保证多实例下每个实例都能向自己的本地连接广播，ws-gateway 的竞拍事件消费者使用广播消费模式。

配置建议：

```Plaintext
Topic: auction_event
ConsumerGroup: ws-gateway-auction-broadcast
MessageModel: BROADCASTING
Tags: auction_started || bid_accepted || auction_finished || auction_failed || auction_cancelled
```

处理规则：

1. `auction_expire_check` 是 auction-service 内部延迟检查事件，ws-gateway 不订阅或直接忽略。

2. 消息必须包含 `room_id`，否则不能广播并记录错误日志。

3. ws-gateway 将 auction-service 事件转换为 WebSocket 广播消息，保留 `event_id`、`auction_id`、`room_id`、`version` 和核心竞拍数据。

4. 同一实例内可以用短期内存缓存按 `event_id` 去重，避免 MQ 重试导致重复广播。

5. 不使用全局 Redis `SET NX` 对竞拍事件去重，否则会导致广播消费模式下只有一个实例能广播，其他实例本地连接收不到消息。

6. 客户端应按 `event_id` 或 `auction_id + version` 做最终去重和防旧覆盖。

## 十、错误码

|code|说明|
|---|---|
|0|成功|
|400|消息格式错误或参数错误|
|401|未登录或 token 无效|
|403|无权执行该操作|
|404|直播间或竞拍不存在|
|409|业务请求未被接受，例如出价失败|

在线状态仍由 ws-gateway 在用户进入、心跳、离开和超时清理时实时写入 Redis；面向客户端的 `room_online_changed` 展示消息不要求每次 Redis 变化都立即广播，而是由 ws-gateway 按房间聚合后默认每 3 秒最多推送一次最新人数。聚合 ticker 放在 ws-gateway 内部，因为只有 ws-gateway 持有本地 WebSocket 连接和房间订阅关系，api-gateway 不参与长连接管理，也不订阅房间在线状态。

如果 3 秒窗口内同一房间发生多次进入、离开或超时清理，ws-gateway 只保留该房间的最新待推送标记；flush 时重新从 Redis 读取最新 `online_user_count` 和 `connection_count`，再向本实例内对应直播间连接广播。连续两个展示周期人数和连接数都未变化时不重复广播。

## 十二、本期不实现

1. 不实现弹幕、私聊、礼物、点赞、红包等直播互动能力。

2. 不持久化 WebSocket 消息和广播事件。

3. 不实现离线消息补发；用户断线期间错过的竞拍状态通过重新查询 auction-service 获取。

4. 不实现主动踢人、封禁、黑名单和风控策略。

5. 不实现跨直播间广播、人群标签广播和运营后台指令。

6. 不由 ws-gateway 生成订单或处理支付。
