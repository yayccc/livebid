# WebSocket 直播互动协议 v1

> Status: proposed
> Current-code: V1 消息类型已实现；interaction-service、`room_seq`、离线互动和新 recent 流程尚未实现。
> Authority: 本文负责客户端与 ws-gateway 之间的公开互动 JSON。
> Non-authority: 规范消息、内部 RPC、Redis 和 AI 策略由直播互动专题负责。
> Updated-at: 2026-07-17 +08:00

本文在现有 V1 类型上追加场次和弱顺序字段，不要求客户端同步更换消息类型。当前代码已经支持 `send_danmaku`、`danmaku_created` 和 `ai_interaction_created`，但尚未接入 interaction-service、`room_seq`、离线房间互动和新 recent 合并流程。

## 一、兼容规则

- 客户端忽略未知字段；服务端只追加 optional 字段。
- `server_time` 使用 Unix 毫秒。
- 发送响应和房间广播的到达顺序没有保证，客户端按 `message_id` 去重。
- `room_seq` 只用于同一房间弱排序，允许间隙，不等待无限补洞。
- 用户消息的 `live_session_id` 可空；AI 消息必须有该字段。

## 二、发送消息

客户端请求保持不变：

```json
{
  "type": "send_danmaku",
  "request_id": "req_dm_10000001",
  "timestamp": 1780000000000,
  "data": {
    "content": "现在到多少钱了？"
  }
}
```

规则：

1. 必须登录，`request_id` 在同一次重试中保持不变。
2. 连接必须绑定已发布且允许互动的房间；不再以 `living` 或媒体在线为必要条件。
3. 内容去除首尾空白后满足服务端长度和安全规则。
4. 网关只做 JSON 与连接身份校验，然后调用 `PublishUserMessage`；不得本地写 recent、分配 ID/序号或先广播。

成功响应：

```json
{
  "type": "response",
  "request_id": "req_dm_10000001",
  "request_type": "send_danmaku",
  "code": 0,
  "message": "success",
  "server_time": 1780000001000,
  "data": {
    "message_id": "msg_10000001",
    "room_id": 4001,
    "live_session_id": 910000000001,
    "room_seq": 81
  }
}
```

离线房间成功响应省略 `live_session_id`。幂等重试返回相同 `message_id` 和 `room_seq`。

## 三、用户消息广播

消息类型继续使用 `danmaku_created`：

```json
{
  "type": "danmaku_created",
  "event_id": "evt_10000001",
  "room_id": 4001,
  "live_session_id": 910000000001,
  "room_seq": 81,
  "server_time": 1780000001000,
  "data": {
    "message_id": "msg_10000001",
    "sender_type": "user",
    "user_id": 9001,
    "nickname": "张三",
    "content": "现在到多少钱了？",
    "content_type": "text",
    "status": "visible"
  }
}
```

离线消息省略 `live_session_id`，其余结构一致。

## 四、AI 消息广播

消息类型继续使用 `ai_interaction_created`：

```json
{
  "type": "ai_interaction_created",
  "event_id": "evt_10000002",
  "room_id": 4001,
  "live_session_id": 910000000001,
  "room_seq": 82,
  "server_time": 1780000002200,
  "data": {
    "message_id": "msg_10000002",
    "sender_type": "ai_assistant",
    "assistant_role": "live_assistant",
    "display_name": "AI互动助手",
    "action_type": "answer",
    "content": "当前价以页面实时显示为准，现在是 1200 元。",
    "content_type": "text",
    "reply_to_message_ids": ["msg_10000001"],
    "status": "visible"
  }
}
```

前端必须显示 AI 特殊标识，不得把 `ai_assistant` 渲染成真人或主播。无法识别的新 `action_type` 时仍可按普通 AI 文本展示。

## 五、连接 recent

连接成功响应保留 `recent_danmaku` 字段，以兼容现有客户端；目标实现由网关在“订阅房间频道成功后”查询 interaction recent，再与订阅期间事件合并：

```json
{
  "type": "response",
  "request_type": "connect",
  "code": 0,
  "server_time": 1780000003000,
  "data": {
    "room_id": 4001,
    "latest_room_seq": 82,
    "recent_danmaku": [
      {
        "message_id": "msg_10000001",
        "live_session_id": 910000000001,
        "room_seq": 81,
        "sender_type": "user",
        "user_id": 9001,
        "nickname": "张三",
        "content": "现在到多少钱了？",
        "content_type": "text",
        "server_time": 1780000001000
      }
    ]
  }
}
```

recent 按 `room_seq` 升序，只是轻量补偿；客户端不能据此请求无限历史。

## 六、错误码

| code | 场景 |
| --- | --- |
| `400` | JSON/字段/内容非法 |
| `401` | 未登录或用户身份无效 |
| `403` | 房间不可访问、互动关闭或无权发送 |
| `409` | 当前房间/场次前置条件冲突 |
| `429` | 用户频控 |
| `500` | 非预期内部错误 |
| `503` | interaction-service、live-service 或 Redis 必要依赖不可用 |

`request_id` 必须原样回传。确定的 `400/401/403/409/429` 不建议自动重试；连接异常或 `503` 可在短时间内使用原 `request_id` 重试。

## 七、目标处理链路

```text
client send_danmaku
-> ws-gateway protocol/auth adapter
-> interaction-service gRPC
-> response to sender

interaction room event
-> ws-gateway dynamic room subscription
-> local connections as danmaku_created / ai_interaction_created
```

具体频道和“先订阅、再 recent、再合并”的竞态处理以 [实时分发契约](../../features/live-interaction/contracts/实时分发-v1.md) 为准。
