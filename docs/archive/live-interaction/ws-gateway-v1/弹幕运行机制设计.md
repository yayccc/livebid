# 弹幕运行机制设计（ws-gateway V1 归档）

> Status: superseded。本文只追溯 ws-gateway V1，不能指导新实现。现行目标见 `docs/features/live-interaction/README.md`。

## 一、服务端处理流程

### 用户发送弹幕

```text
1. handleMessage 识别 type=send_danmaku。
2. 校验 conn.UserID > 0。
3. 校验 request_id 非空，解析 data.content，trim 后校验 1 到 30 个字符。
4. 校验直播间当前状态仍为 living。
5. 检查 request_id 幂等缓存；命中则直接返回首次 message_id。
6. 执行 Redis 频控。
7. 获取连接缓存昵称；缺失时查询或读取昵称缓存。
8. 生成 message_id、event_id、server_time。
9. 写 request_id 幂等缓存。
10. 构造 danmaku_created 广播消息。
11. 写 Redis 最近弹幕。
12. 向本实例 room_id 连接广播。
13. 发布 Redis Pub/Sub 跨实例广播。
14. 按配置发布 danmaku.created 给 ai-service，可选择 Redis Pub/Sub、RocketMQ 或同时发布。
15. 向发送者返回 send_danmaku 成功响应。
```

成功响应可以在广播前或广播后发送。第一版建议完成本地广播和最近弹幕写入后响应，AI 事件投递失败不影响响应。

## 二、直播间状态校验

发送弹幕必须确认直播间仍处于 `living` 状态，不能只依赖连接建立时校验。

```text
Key: ws:room:{room_id}:live_status
Type: String
TTL: 5 秒
Value: living / not_live / ended
```

校验规则：

1. 发送弹幕时先读 Redis 房间状态缓存。
2. 缓存命中 `living` 时允许继续处理。
3. 缓存未命中时调用 `live-service.GetLiveRoom` 获取状态，并写入短 TTL 缓存。
4. 状态不是 `living` 时返回 `403`，不广播，不写最近弹幕，不发布 AI 事件。
5. Redis 状态缓存读取失败时降级为直接调用 `live-service`；`live-service` 也失败时返回 `500`。
6. 后续接入直播结束事件后，可在收到 `live.ended` 时主动清理房间状态缓存并关闭或清理对应房间连接。

## 三、请求幂等

`request_id` 用于短期幂等，避免客户端重试造成重复弹幕。

```text
Key: ws:room:{room_id}:danmaku:req:{user_id}:{request_id}
Type: String
TTL: 60 秒
Value: {"message_id":"dm_10000001","room_id":4001}
```

处理规则：

1. `request_id` 不能为空。
2. 频控前先检查幂等缓存；如果命中，直接返回首次成功的 `message_id`，不重复广播，不重复发布 AI 事件，也不触发频控。
3. 新弹幕通过校验并生成 `message_id` 后写入幂等缓存。
4. 幂等缓存写入失败时返回 `500`，避免成功广播后客户端重试产生重复消息。

## 四、发送频控

```text
Key: ws:room:{room_id}:danmaku:rate:user:{user_id}
Type: String
TTL: 1 秒
```

第一版规则：

1. 同一用户在同一直播间 1 秒最多发送 1 条。
2. 使用 Redis `SET key 1 NX EX 1` 实现。
3. 命中频控返回 `429`，不广播，不写最近弹幕，不发布 AI 事件。
4. 频控 Redis 失败时返回 `500`，不广播、不写最近弹幕、不发布 AI 事件。

后续如需要更细粒度频控，可扩展为滑动窗口或令牌桶。

## 五、昵称缓存

弹幕第一版不展示头像，只展示昵称。

昵称来源：

1. 连接建立时如 JWT 或用户上下文中已有昵称，则写入连接对象。
2. 如果连接建立时没有昵称，首次发送弹幕时调用 `user-service.GetUser` 查询昵称，并缓存到连接对象或 Redis。
3. 后续弹幕广播优先使用缓存昵称，不在每条弹幕广播时查询用户服务。

Redis 缓存：

```text
Key: ws:user:nickname:{user_id}
Type: String
TTL: 10 到 30 分钟
Value: 用户展示昵称
```

`ws-gateway` 需要新增 `user-service` gRPC client：

```text
Config: WS_GATEWAY_USER_SERVICE_TARGET
Default: 127.0.0.1:9004
RPC: livebid.user.v1.UserService.GetUser
Timeout: 复用 ws-gateway RPC timeout，默认 3 秒
```

用户服务不可用、查询失败或昵称为空时，使用脱敏兜底昵称，例如 `用户{user_id后4位}`，继续发送弹幕，并记录 warn 日志。

## 六、最近弹幕

```text
Key: ws:room:{room_id}:danmaku:recent
Type: List
Length: 10
TTL: 直播结束后 24 小时
Value: danmaku_created 广播消息 JSON
```

写入规则：

1. 弹幕通过校验后写入最近弹幕。
2. 使用 `LPUSH` 写入，`LTRIM 0 9` 保留最近 10 条。
3. 连接响应读取最近弹幕时，使用 `LRANGE 0 9` 后按 `server_time` 正序返回。
4. 写入失败只记录日志，不阻断实时广播。
5. 最近弹幕用于新进入直播间展示，不作为完整历史记录。

## 七、跨实例广播

```text
Channel: ws:room:{room_id}:danmaku
Payload: danmaku_created 广播消息 JSON
```

处理规则：

1. 发送弹幕的实例先向本地房间连接广播。
2. 再向 Redis Pub/Sub 发布 `danmaku_created`。
3. 其他 `ws-gateway` 实例订阅后向本实例相同 `room_id` 连接广播。
4. 每个实例按 `message_id` 做短期本地去重，避免重复广播。
5. Redis Pub/Sub 发布失败时保留本实例广播结果，记录 warn 日志和指标，不回滚、不重试主请求；其他实例用户可能收不到该条弹幕。

弹幕跨实例广播使用 Redis Pub/Sub，不使用 RocketMQ 广播模式。AI 互动助手和后续审计、统计、风控等服务消费链路可按配置选择 Redis Pub/Sub、RocketMQ 或同时发布。

## 八、失败策略

| 场景 | 策略 |
| --- | --- |
| 房间状态缓存 Redis 读取失败 | 降级调用 `live-service.GetLiveRoom` |
| 房间状态缓存和 live-service 均失败 | 返回 `500`，不广播 |
| request_id 幂等缓存读取或写入失败 | 返回 `500`，不广播 |
| 频控 Redis 失败 | 返回 `500`，不广播 |
| 用户昵称查询失败 | 使用兜底昵称，继续发送 |
| 最近弹幕写入失败 | 记录日志，继续广播 |
| 弹幕跨实例 Pub/Sub 发布失败 | 保留本实例广播，记录日志和指标 |
| AI 输入事件投递失败 | 记录日志和指标，不影响弹幕发送结果 |

## 九、配置项

| 配置项 | 说明 | 默认值 |
| --- | --- | --- |
| `WS_GATEWAY_DANMAKU_ENABLED` | 是否启用弹幕 | `true` |
| `WS_GATEWAY_DANMAKU_MAX_CHARS` | 弹幕最大字符数 | `30` |
| `WS_GATEWAY_DANMAKU_RECENT_LIMIT` | 最近弹幕条数 | `10` |
| `WS_GATEWAY_DANMAKU_RATE_LIMIT_SECONDS` | 同用户同房间发送间隔 | `1` |
| `WS_GATEWAY_DANMAKU_RECENT_TTL_HOURS` | 最近弹幕缓存 TTL | `24` |
| `WS_GATEWAY_DANMAKU_REQUEST_TTL_SECONDS` | `request_id` 幂等缓存 TTL | `60` |
| `WS_GATEWAY_ROOM_STATUS_CACHE_TTL_SECONDS` | 直播间状态缓存 TTL | `5` |
| `WS_GATEWAY_USER_SERVICE_TARGET` | user-service gRPC 目标地址 | `127.0.0.1:9004` |

## 十、实现落点

| 模块 | 改动 |
| --- | --- |
| `internal/handler/message.go` | 新增消息类型、广播类型、请求/响应数据结构、`429` 错误码 |
| `internal/handler/websocket.go` | 新增 `handleSendDanmaku`，接入 `handleMessage` 分发 |
| `internal/handler/hub.go` | 复用 `BroadcastRoom`，必要时新增房间是否活跃判断 |
| `internal/repository` | 新增弹幕 Redis repository，处理最近弹幕、频控、幂等、房间状态缓存、Pub/Sub |
| `internal/client/user.go` | 新增 user-service gRPC client，用于首次弹幕昵称查询 |
| `internal/config` | 新增弹幕配置 |
| `internal/bootstrap` | 启动弹幕 Pub/Sub 订阅 |

## 十一、非功能要求

1. 弹幕广播不能阻塞竞拍事件广播。
2. 单连接写队列满时，弹幕可以被丢弃或连接被关闭；竞拍事件优先保留。
3. Redis 最近弹幕写失败不影响实时广播。
4. AI 事件投递失败不影响实时广播。
5. 用户弹幕内容进入日志时不得输出完整长文本，避免日志污染和敏感内容扩散。
6. 客户端断线期间错过的弹幕不补发，只在重连后获取最近 10 条。
