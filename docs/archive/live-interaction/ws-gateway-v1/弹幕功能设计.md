# 直播间弹幕功能设计（ws-gateway V1 归档）

> Status: superseded。本文只追溯 ws-gateway V1；网关直管业务和 Redis/RocketMQ 双链路不是目标方案。现行目标见 `docs/features/live-interaction/README.md`。

本文是弹幕功能设计总览。详细协议、运行机制和 AI 对接拆到独立文档，避免单个文档过长。

## 一、设计目标

弹幕功能基于现有 `ws-gateway` 扩展，不新增独立长连接入口。客户端仍通过：

```text
GET /ws/live?room_id={room_id}&token={access_token}
```

进入直播间，弹幕作为 WebSocket 消息类型接入。

第一版目标：

1. 支持登录用户发送文本弹幕。
2. 支持直播间维度实时广播。
3. 支持多 `ws-gateway` 实例间弹幕同步。
4. 支持最近 10 条弹幕缓存。
5. 支持用户维度频控和基础内容校验。
6. 支持将用户弹幕事件提供给 `ai-service` 消费。
7. 支持 AI 互动助手消息回到直播间展示的传输通道，并与普通用户弹幕区分。

## 三、整体链路

```text
用户 WebSocket send_danmaku
  -> ws-gateway 校验登录、房间、内容、幂等、频控
  -> 获取或缓存用户昵称
  -> 生成 message_id / event_id / server_time
  -> 写入最近弹幕缓存
  -> 广播给当前实例房间连接
  -> Redis Pub/Sub 通知其他 ws-gateway 实例
  -> 按配置发布 danmaku.created 事件给 ai-service
```

AI 互动助手消息回流：

```text
ai-service 生成直播间 AI 消息
  -> RocketMQ: ai_interaction.created
  -> 一个 ws-gateway 实例集群消费
  -> Redis Pub/Sub fanout 到所有 ws-gateway 实例
  -> 广播 ai_interaction_created 到对应直播间
```

## 四、核心决策

1. 弹幕跨 `ws-gateway` 实例广播固定使用 Redis Pub/Sub，不使用 RocketMQ 广播模式。
2. AI 互动助手输入支持 `redis_pubsub`、`rocketmq`、`both` 三种模式，联调和压测后再确定默认方案。
3. AI 消息回流固定使用“RocketMQ 集群消费到一个 ws-gateway，再 Redis Pub/Sub fanout 到所有 ws-gateway”的拓扑。
4. 发送弹幕时必须校验直播间当前仍为 `living`，不能只依赖连接建立时校验。
5. `request_id` 做 60 秒短 TTL 幂等，避免客户端重试重复广播。
6. 弹幕第一版不展示头像，只展示昵称；昵称优先缓存，用户服务失败时使用兜底昵称。
7. 最近弹幕返回顺序固定为 `server_time` 正序，旧消息在前、新消息在后。
8. `ws-gateway` 不判断 AI 自动回复策略，也不处理商家确认流程；这些由 `ai-service` 和商家后台负责。

## 五、本期不做

1. 不做完整弹幕历史存储。
2. 不做管理员撤回。
3. 不做禁言。
4. 不做 AI 自动回复策略判断。
5. 不做 AI 消息人工确认流程。
6. 不做热门房间弹幕分片和降采样。
