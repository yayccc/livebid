# 直播间互动服务需求（2026-07-16 草案归档）

> Status: superseded。本文是 2026-07-16 的未实施草案，已被 `docs/features/live-interaction/` 与拆分后的服务文档取代，不能作为现行需求。

## 一、背景与目标

`interaction-service` 是直播间公开互动消息的业务服务。第一阶段只承载文本弹幕和 AI 互动助手公开消息，后续可以扩展撤回、禁言、审核、点赞和运营互动能力。

本服务的核心目标是：

1. 为直播间提供低延迟文本互动能力。
2. 将弹幕业务规则从 `ws-gateway` 中抽离，避免长连接服务同时承担业务状态和 AI 对接职责。
3. 为用户消息和 AI 消息建立统一的消息 ID、房间序号、短历史和广播链路。
4. 向 `ai-service` 提供低延迟、允许丢失、只关注新鲜消息的输入流。
5. 保证 AI 消息经过可信服务入口写入，并始终带有明确的 AI 身份标识。

弹幕属于直播间氛围消息，不参与出价、成交、订单或支付判定。系统优先保证低延迟和可用性，不追求全局强顺序、离线必达和完整历史。

## 二、产品场景

### 2.1 用户弹幕

1. 登录用户可以在已发布且允许互动的房间发送文本弹幕；房间未开播时消息不携带直播场次。
2. 游客可以观看弹幕，但第一阶段不能发送。
3. 消息通过准入和内容规则后，应尽快广播给同一直播间的在线用户。
4. 用户进入或重连直播间时，可以获取该持久房间最近 10 条公开互动消息。
5. 最近消息同时包含用户和 AI 消息，使新进入用户能够看到完整的近期问答上下文。

### 2.2 AI 互动消息

1. `ai-service` 可以观察已接纳的真人弹幕，并选择性生成公开回答或氛围消息。
2. AI 不保证处理或回答每条弹幕，输入丢失、过期或被采样均属于正常行为。
3. AI 消息必须显示为 `ai_assistant`，不能伪装成真实用户。
4. AI 消息必须经过 `interaction-service` 的内部 gRPC 接口写入，不能由 `ai-service` 直接发布房间 Redis 消息。
5. AI 消息与用户弹幕共享房间序号和最近消息列表，但不会再次进入 AI 输入流。

## 三、服务边界

| 服务 | 负责 | 不负责 |
| --- | --- | --- |
| `ws-gateway` | WebSocket 鉴权、连接管理、外部协议适配、调用互动 RPC、订阅房间频道、本地广播 | 弹幕频控、幂等、消息 ID、短历史、AI 策略 |
| `interaction-service` | 消息准入、内容规则、幂等、频控、消息 ID、`room_seq`、短历史、Redis fan-out、AI 输入发布 | LLM 调用、是否回答、RAG、竞拍规则判定 |
| `ai-service` | 房间上下文、采样、聚合、候选排序、工具/RAG 路由、回复决策和生成 | 用户弹幕准入、房间广播、竞拍事实判定 |
| `live-service` | 直播间和当前直播场次事实 | 互动消息和 AI 策略 |
| `auction-service` | 当前价、加价幅度、倒计时、竞拍状态等权威事实 | 根据弹幕生成自然语言回答 |
| `goods-service` | 商品结构化基础信息 | 直播间互动状态 |

## 四、功能需求

### 4.1 发布用户消息

`ws-gateway` 调用内部 gRPC 发布用户弹幕。`interaction-service` 必须：

1. 校验调用来源、`room_id`、用户身份、`request_id` 和文本内容。
2. 校验房间已发布且 `chat_enabled=true`，并解析可选的当前直播场次。
3. 按用户和房间执行短期幂等与发送频控。
4. 执行基础敏感词、空内容和长度规则。
5. 生成规范化 `message_id`、`event_id`、`room_seq` 和服务端时间。
6. 写入有界最近消息。
7. 发布房间实时广播事件。
8. 将已接纳的真人消息发布到 AI 输入频道。
9. 返回规范化消息；幂等重试必须返回第一次成功的同一条消息。

### 4.2 发布 AI 消息

`ai-service` 调用内部 gRPC 发布 AI 消息。`interaction-service` 必须：

1. 只接受可信 `ai-service` 身份调用。
2. 使用 `decision_id` 做短期幂等。
3. 校验 `room_id`、`live_session_id`、消息新鲜度和当前直播状态。
4. 只接受 `ANSWER`、`ATMOSPHERE`、`REDIRECT` 三类可展示动作。
5. 固定生成 AI 发送者类型和展示名称，不信任调用方传入身份字段。
6. 生成 `message_id`、`event_id`、`room_seq` 并写入最近消息。
7. 发布与用户消息相同的房间广播频道。
8. 不将 AI 消息再次发布到 AI 输入频道。

### 4.3 查询最近消息

1. `ws-gateway` 建立连接时通过内部 gRPC 获取该房间最近消息。
2. 第一阶段默认返回 10 条，按 `room_seq` 升序排列。
3. 最近消息只用于进入直播间展示和轻量重连恢复，不是完整历史或可靠消费日志。
4. 用户和 AI 消息使用统一结构返回，客户端按 `sender_type` 展示不同身份。

### 4.4 房间实时广播

1. `interaction-service` 将已接纳消息发布到 Redis Pub/Sub 房间频道。
2. `ws-gateway` 只订阅本实例存在本地连接的房间。
3. 某实例第一个连接进入房间时建立订阅，最后一个连接离开后延迟取消订阅。
4. Redis Pub/Sub 发布或订阅中断可能导致部分在线用户漏收，系统不进行离线补发。

### 4.5 AI 实时输入

1. 只发布已接纳且 `sender_type=user` 的消息。
2. 唯一事件名称固定为 `interaction.user_message.accepted.v1`，字段以 `弹幕功能设计.md` 为准。
3. 输入固定使用 Redis Pub/Sub，不提供 `redis_pubsub|rocketmq|both` 双链路开关。
4. 事件必须包含过期时间；`ai-service` 收到过期消息后直接丢弃。
5. AI 服务不可用、订阅断开或事件发布失败，不影响用户弹幕发送结果。

## 五、业务规则

### 5.1 身份与准入

1. 用户身份来自 `ws-gateway` 已验证的连接上下文，不能信任客户端消息体中的 `user_id`。
2. `ws-gateway` 可以传递连接中缓存的昵称快照；互动服务负责裁剪、限制和兜底，不在每条消息热路径同步查询用户服务。
3. `ai-service` 不能指定 `sender_type`、用户 ID 或展示名称。
4. 用户消息可以在已发布且允许互动的离线房间写入；AI 消息必须匹配当前直播场次，直播结束或场次切换后拒绝迟到回复。

### 5.2 内容限制

| 消息类型 | 第一阶段默认限制 |
| --- | --- |
| 用户文本弹幕 | 去除首尾空白后 1 到 30 个字符 |
| AI 公开消息 | 去除首尾空白后 1 到 80 个字符 |

两类限制分别配置。AI 回答应保持适合直播间快速阅读的长度，不承载长篇客服对话。

### 5.3 幂等与频控

1. 用户消息幂等键为房间、用户和 `request_id`，默认保留 60 秒。
2. 同一用户在同一房间默认 1 秒最多发送 1 条。
3. AI 消息幂等键为当前场次和 `decision_id`，重复调用返回第一次生成的消息。
4. `room_seq` 在持久直播间内单调递增，允许因失败或并发产生间隙，不代表消息可靠投递。

### 5.4 房间与直播场次

`room_id` 表示长期存在的互动空间，`live_session_id` 表示一次实际业务开播。两者不能互相替代：

1. 房间连接、广播、`room_seq`、最近消息、用户幂等和用户频控按 `room_id` 维护。
2. AI 上下文、冷却、已回答意图、生成任务和 AI 回写幂等按 `live_session_id` 隔离。
3. 用户消息始终包含 `room_id`；只有房间正在业务直播时才携带 `live_session_id`。
4. AI 默认只消费携带有效 `live_session_id` 的真人消息。
5. `live-service` 在 `StartLive` 时生成稳定的 `current_live_session_id`，SRS 推流回调不得生成或切换场次。

## 六、投递与一致性语义

| 链路 | 语义 |
| --- | --- |
| `ws-gateway -> interaction-service` | 同步 gRPC；调用失败时用户消息不在网关本地先广播 |
| 互动服务幂等与短历史 | Redis 原子操作；成功后消息视为已接纳 |
| 房间 Redis Pub/Sub | at-most-once、低延迟、允许部分在线实例漏收 |
| AI 输入 Redis Pub/Sub | at-most-once、允许丢失、不积压、不补偿 |
| `ai-service -> interaction-service` | 同步 gRPC；在消息新鲜度内使用同一 `decision_id` 短重试 |

用户发送成功的提交点是：互动服务完成准入、幂等记录和短历史写入。房间 fan-out 和 AI 输入发布失败不回滚已接纳消息，但必须记录日志和指标。

## 七、非功能要求

1. 用户弹幕 gRPC 热路径不等待 AI、RocketMQ、RAG 或模型调用。
2. 弹幕写入和广播不能阻塞竞拍核心事件发送。
3. Redis 不可用时返回服务不可用，不在 `ws-gateway` 降级生成第二套消息 ID 或本地业务状态。
4. 单连接写队列拥塞时可以丢弃弹幕；竞拍价格和成交事件优先级更高。
5. 用户内容不得完整写入普通日志；排障日志优先记录消息 ID、长度、哈希和规则结果。
6. 所有调用和事件透传 `trace_id`，便于关联用户请求、AI 决策和最终广播。
7. 第一阶段不引入 MySQL 长期保存互动消息。

## 八、本期范围

### 8.1 本期实现

1. 用户文本弹幕发布和统一广播。
2. 用户和 AI 消息统一模型。
3. 持久房间最近 10 条互动消息。
4. 用户幂等、频控和基础内容规则。
5. `room_seq` 弱顺序标识。
6. Redis Pub/Sub 房间 fan-out。
7. Redis Pub/Sub AI 实时输入。
8. AI 消息 gRPC 回流和 `decision_id` 幂等。

### 8.2 本期不实现

1. 私聊和私人 AI 问答。
2. 完整历史查询和离线消息补发。
3. 禁言、撤回、人工审核和申诉。
4. 图片、语音、视频和表情包消息。
5. 将 RocketMQ 或 Kafka 作为实时弹幕和 AI 输入主链路。
6. 由互动服务判断 AI 是否应回复或维护气氛。

## 九、验收标准

1. 相同用户、场次和 `request_id` 重试只产生一个 `message_id`。
2. 用户消息和 AI 消息在同一持久直播间中获得单调递增的 `room_seq`。
3. 房间最近消息同时包含用户和 AI 消息，返回顺序稳定。
4. AI 输入只包含真人消息，AI 回复不会形成自触发回环。
5. AI 服务停机不影响用户弹幕正常发送和广播。
6. 离线房间允许用户互动但不触发直播 AI；直播场次切换后，旧场次 AI 回复不能写入新场次。
7. 多 `ws-gateway` 实例只向持有目标房间连接的实例发送房间消息。
8. Redis 发布失败、gRPC 失败和幂等命中均有可区分的指标。

## 十、实施前待确认

1. AI 公开消息 80 字默认限制是否满足前端展示。
2. 基础敏感词词库来源，以及命中后的错误码和运营记录要求。
3. 第一阶段使用普通 Redis Pub/Sub，还是直接按 Redis Cluster 7 的 Sharded Pub/Sub 设计频道和连接管理。
