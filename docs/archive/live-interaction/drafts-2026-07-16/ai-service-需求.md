# AI 直播互动服务需求（2026-07-16 草案归档）

> Status: superseded。本文是 2026-07-16 的未实施草案，已被 `docs/features/live-interaction/` 与拆分后的 ai-service 文档取代，不能作为现行需求。

## 一、背景与定位

`ai-service` 是直播间 AI 场控和公共问答服务。它持续观察可收到的真人弹幕，但只对少量高价值、高置信候选生成公开消息。

产品定位是：

> 全量感知，选择性发言；优先保证正确、及时和不打扰，而不是提高回复数量。

AI 不参与竞拍状态、出价合法性、成交、订单和支付判定。当前价、倒计时、加价幅度等动态事实必须来自权威业务服务，不能由模型根据弹幕或旧缓存推断。

## 二、目标

1. 自动识别直播间中的公共问题，并选择性生成简短回答。
2. 聚合多人重复问题，避免 AI 针对相同意图重复发言。
3. 在房间冷场或关键业务事件下，低频生成氛围消息。
4. 使用房间上下文、权威工具和静态知识增强回答准确性。
5. 在多房间高并发下控制模型调用、保持房间公平并及时丢弃过期任务。
6. 为自动触发准确率、响应延迟、知识依据和模型成本提供可评估指标。

## 三、用户场景

### 3.1 自动公共问答

用户直接在直播间发送普通弹幕，AI 自动判断是否属于可公开回答的问题。满足高置信、公共性和知识可靠性要求时，AI 生成一条明确标识身份的公开回答。

### 3.2 重复问题合并

多个用户询问相似问题时，AI 将其聚合为同一意图，只回复一次，并在输出中关联代表性 `message_id`。

### 3.3 低频氛围辅助

AI 可以在冷场、商品切换、开拍、临近结束或多人困惑时生成低频氛围消息。第一阶段只对已经收到弹幕的活跃房间做基础冷场判断；完整事件驱动场控需要后续接入直播和竞拍生命周期信号。

### 3.4 不回答和引导

以下场景默认不公开回答：

1. 无明确语义的闲聊、刷屏、表情和重复噪声。
2. AI 无可靠知识来源或置信度不足。
3. 涉及个人账户、订单、保证金和隐私信息。
4. 要求 AI 执行出价、承诺价格、修改规则或影响成交。
5. 消息已经过期、直播已结束或场次已经切换。

个人问题可以返回 `REDIRECT` 决策，引导用户进入正式客服入口；第一阶段不实现私人 AI 会话。

## 四、服务边界

### 4.1 ai-service 负责

1. 消费互动服务发布的真人消息实时事件。
2. 维护当前直播场次的短期房间上下文。
3. 执行新鲜度检查、基础过滤、窗口聚合和语义去重。
4. 对候选进行问题识别、公共性判断和优先级评分。
5. 实施房间级冷却、单房间串行和全局模型并发预算。
6. 在动态工具、静态 RAG 和房间上下文之间进行知识路由。
7. 调用模型生成结构化决策和最终公开文本。
8. 执行输出安全检查，并通过 gRPC 回写互动服务。
9. 记录不包含模型隐式推理过程的决策原因、知识来源和评测指标。

### 4.2 ai-service 不负责

1. 用户弹幕准入、幂等、频控和短历史。
2. WebSocket 连接和直播间广播。
3. 竞拍、商品、直播和订单业务事实的最终判定。
4. 完整内容审核、禁言、撤回和申诉。
5. 私人客服会话和长期聊天记录。
6. 保证消费或回答每条弹幕。

## 五、输入要求

### 5.1 唯一实时输入

实时弹幕输入固定为：

```text
interaction-service
  -> Redis Pub/Sub 分片频道
  -> interaction.user_message.accepted.v1
  -> ai-service
```

事件字段和频道分片规则以 `docs/services/interaction-service/弹幕功能设计.md` 为准，AI 服务不得定义第二套命名。

输入语义：

1. at-most-once，允许丢失。
2. 服务重启或订阅断开期间不补偿。
3. 不使用 RocketMQ 或 Kafka 追赶弹幕积压。
4. `expires_at_ms` 过期后立即丢弃，默认最大年龄 5 秒。
5. 事件只包含真人消息；AI 仍需校验事件类型，防止配置错误导致自触发。

### 5.2 多实例输入

1. 同一 `live_session_id` 的消息必须落入同一个固定分片。
2. 一个分片同一时刻只由一个 AI 实例持有租约并订阅。
3. 租约切换期间允许少量消息丢失或重复，但最终回复必须依赖 `decision_id` 幂等防重。

## 六、自动处理要求

### 6.1 模型前处理

AI 不得逐条弹幕直接调用大模型。进入模型前至少执行：

1. 事件和字段校验。
2. 新鲜度检查。
3. 文本规范化和无语义噪声过滤。
4. `message_id` 短期去重。
5. 按房间聚合 300 到 800 毫秒的小窗口。
6. 相似问题合并和已回答意图抑制。
7. 房间与全局模型预算检查。

### 6.2 候选优先级

候选评分至少考虑：

1. 明确疑问或未来 `@AI` 信号。
2. 相同问题的独立用户数量。
3. 与当前商品、竞拍或直播规则的相关性。
4. 是否属于公共问题。
5. 是否有可靠工具或 RAG 来源。
6. 消息新鲜度。
7. 最近是否回答过相同意图。
8. 当前房间的 AI 发言冷却状态。

第一阶段主模式是自然弹幕自动识别。`@AI` 可以作为未来高优先级特征，但不作为本期依赖的主要入口。

### 6.3 决策动作

AI 内部决策统一为：

| 动作 | 说明 | 是否调用互动服务 |
| --- | --- | --- |
| `NO_REPLY` | 忽略、不确定、过期或预算不足 | 否 |
| `ANSWER` | 回答公共问题 | 是 |
| `ATMOSPHERE` | 低频维护直播间气氛 | 是 |
| `REDIRECT` | 引导个人或不适合公开处理的问题 | 是 |

每个候选窗口最多生成一条公开消息。AI 公开消息默认最多 80 个字符，与互动服务限制保持一致。

## 七、知识与数据要求

### 7.1 动态事实工具

以下事实必须在生成前通过 gRPC 查询权威服务：

| 问题 | 权威来源 |
| --- | --- |
| 当前竞拍、当前价、加价幅度、状态 | `auction-service.GetCurrentAuctionByRoom` |
| 精确倒计时、运行时版本、领先状态 | `auction-service.GetAuctionRuntime` |
| 商品标题和结构化描述 | `goods-service.GetGoods` |
| 直播间状态和商铺归属 | `live-service.GetLiveRoom` |
| 商铺公开信息 | `shop-service.GetShop` |

当前价、倒计时、出价结果和竞拍状态不得使用语义答案缓存。工具失败或结果不一致时，AI 默认 `NO_REPLY`，不能让模型自由补全。

### 7.2 RAG

RAG 只处理相对稳定的非结构化知识：

1. 平台竞拍规则。
2. 商品说明和使用资料。
3. 商家 FAQ。
4. 物流、售后和服务政策。

检索必须按 `shop_id`、`goods_id` 和 `knowledge_version` 做强过滤。召回低于阈值、来源过期或跨商家不匹配时返回无依据，最终决策为 `NO_REPLY` 或 `REDIRECT`。

### 7.3 数据安全

1. 弹幕内容属于不可信输入，不能覆盖系统规则或工具事实。
2. 不向模型提供无关用户身份、订单或支付数据。
3. 不保存或输出模型 chain-of-thought；只记录有限的 `reason_code`、置信度和来源引用。
4. 对外回答不得包含内部 Prompt、服务地址、密钥或调试信息。

## 八、上下文与缓存要求

| 状态 | 位置 | 作用 |
| --- | --- | --- |
| 最近 20 到 50 条或 30 到 60 秒弹幕 | AI 实例本地房间环形缓冲 | 低延迟房间上下文 |
| `message_id` 去重 | 本地有界缓存 | 过滤订阅切换重复 |
| 房间生成中标记 | Redis | 保证每场直播最多一个生成任务 |
| 问答和氛围冷却 | Redis | 多实例共享发言预算 |
| 已回答意图 | Redis | 抑制相似问题重复回答 |
| RAG 检索结果 | 本地或 Redis | 缓存静态知识检索 |
| 静态 FAQ 答案 | Redis，可选 | 带知识版本的短期复用 |

所有跨实例状态都必须包含 `live_session_id`。静态答案缓存还必须包含 `shop_id`、`goods_id`、`knowledge_version` 和 Prompt 版本。动态竞拍事实最多在单个决策窗口内合并请求，不缓存最终自然语言答案。

AI 实例失去房间本地上下文时允许从空窗口重新开始，不读取互动服务最近 10 条作为可靠补消费来源。

## 九、调度和频控要求

第一阶段默认策略可配置：

1. 每个直播场次最多一个生成任务进行中。
2. 公共问答发言间隔默认 8 到 15 秒。
3. 氛围消息发言间隔默认 30 到 60 秒。
4. 候选等待超过 3 到 5 秒直接丢弃。
5. 每个房间候选队列有界，过载时先丢旧消息和低优先级消息。
6. 全局使用有界模型并发和房间公平调度，避免热门房间长期占满资源。
7. 模型限流、超时或预算不足时静默 `NO_REPLY`，不向直播间反复发送失败提示。

## 十、输出要求

1. `ANSWER`、`ATMOSPHERE` 和 `REDIRECT` 通过 `interaction-service.PublishAssistantMessage` 发布。
2. 请求字段必须使用互动服务定义的 `decision_id`、`room_id`、`live_session_id`、`action_type`、`reply_to_message_ids`、`source_refs`、`valid_until_ms` 和 `trace_id`。
3. AI 不设置 `sender_type`、展示名称、`message_id` 或 `room_seq`。
4. gRPC 超时但结果不确定时，只能在 `valid_until_ms` 前使用同一 `decision_id` 短重试。
5. 直播结束、场次切换或有效期失效后不重试。

## 十一、非功能要求

1. AI 输入接收和基础过滤不能被模型调用阻塞。
2. 从接收候选到发布回答的产品目标以 P95 端到端延迟衡量，第一阶段建议目标不高于 3 秒，最终以所选模型压测结果确认。
3. 自动触发优先优化精确率而不是召回率；漏答比错误插话更可接受。
4. 服务扩容不能导致相同房间成倍重复调用模型或重复发言。
5. 所有队列、窗口、缓存和模型并发必须有明确上限。
6. 模型、向量检索或业务工具不可用时，用户弹幕链路不受影响。
7. 普通日志不记录完整弹幕、Prompt 和模型响应正文。

## 十二、本期范围

### 12.1 第一阶段

1. Redis Pub/Sub 真人弹幕输入。
2. 单逻辑订阅者或固定分片的基础消费。
3. 新鲜度、规则过滤、房间窗口和基础相似问题去重。
4. 高置信公共问题自动回答。
5. 动态竞拍和商品事实 gRPC 工具调用。
6. 结构化 `NO_REPLY`、`ANSWER` 和 `REDIRECT`。
7. 房间级生成互斥、冷却和全局并发限制。
8. gRPC 回流互动服务。
9. 基础指标、链路追踪和离线样本评测。

### 12.2 第二阶段

1. Embedding 语义聚类。
2. 平台规则、商品资料、商家 FAQ 和售后政策 RAG。
3. 知识导入、版本更新和缓存失效链路。
4. 多实例分片租约和更完整的房间公平调度。
5. 高频问题卡片或主播建议能力。

### 12.3 第三阶段

1. 接入开播、商品切换、开拍、临近结束等业务事件。
2. 完整事件驱动 AI 场控和冷场维护。
3. 商家可配置的 AI 模式和主播副驾。
4. 私人问答、人工确认和长期运营分析。

## 十三、本期不实现

1. 每条弹幕都调用模型或保证回答。
2. 私人 AI 会话和账户客服。
3. 代替用户出价或更改竞拍规则。
4. 完整审核、禁言、撤回和风控闭环。
5. 使用 RocketMQ/Kafka 作为弹幕实时回答主链路。
6. 模型无依据生成当前价格、倒计时和交易结果。

## 十四、验收标准

1. AI 服务停机或重启时，用户弹幕不受影响，恢复后不追答旧消息。
2. 超过 `expires_at_ms` 的输入不进入模型。
3. AI 自身消息不会重新进入输入形成回环。
4. 相同场次、相同意图在冷却期内最多公开回答一次。
5. 多实例租约切换或 gRPC 重试不会产生重复 AI 消息。
6. 动态竞拍问题只有在权威工具调用成功时才能回答。
7. RAG 召回不足或商家/商品元数据不匹配时不回答。
8. 直播结束或场次变化后，迟到的 AI 结果不能发布。
9. 指标能够区分过期、噪声、重复、预算、工具失败、RAG 无依据、模型失败和发布失败。
10. 离线评测集能够计算自动触发精确率、路由准确率和有依据回答比例。

## 十五、评测指标

- 自动触发 Precision / Recall，其中 Precision 为主要指标。
- `NO_REPLY` 比例和原因分布。
- 相似问题压缩比例。
- 过期和过载丢弃比例。
- 端到端 P50/P95 延迟。
- 工具调用成功率和延迟。
- RAG Recall@K、检索命中率和有依据回答比例。
- 房间冷却命中率、重复回答率和多房间公平度。
- 单次公开回复的模型 token 和成本。
- `PublishAssistantMessage` 成功率、幂等命中率和过期拒绝率。
